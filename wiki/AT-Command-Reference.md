# AT Command Reference

The CDC-ACM port accepts AT commands, so a node can be reconfigured and
inspected without reflashing. Any serial terminal at 115200 8-N-1 — CDC ignores
the baud rate.

Commands ending `=` set, ending `?` query. Every command answers `OK` or
`ERROR`, with any data on preceding `+VERB:` lines.

A reply of any length arrives whole, with its `OK`, while the host keeps
reading. If the host reads nothing for 500 ms, the rest of that reply is
dropped, and until the host reads again, output that does not fit in the
512-byte transmit buffer is dropped without waiting.

The port also carries log lines (INFO and above), the lines other tasks print
(`+MPING:` per reply, `+MCAST: rx`) and the echo of typed characters. None of
these waits: each goes in whole, or is dropped whole if the transmit buffer
lacks room for it or another line is being written — a reply line included,
which holds the port while it waits for room. They can fall between the lines
of a reply, never inside one, so match reply lines by their `+VERB:` prefix. A
log line longer than 255 bytes is cut to 255, ending in a newline.

The USB-Serial-JTAG console goes dark after early boot — the app hands the
shared USB PHY to USB-OTG for this console — and the mirrored log drops lines
under load, so the diagnostic counters below are the dependable view of the
receive path. That is why there are so many.

> **Three commands need a mesh build.** `AT+MESHSTAT?`, `AT+RXHEAD?` and
> `AT+FCRING?` report a per-frame capture that only `warthog-mesh-smoke` and
> the `warthog-mesh-sae*` envs built on it record (`WARTHOG_MESH_RX_TAP`); on
> other builds they answer
> `+ERR: built without WARTHOG_MESH_RX_TAP` rather than reporting an empty
> capture as though nothing were arriving. Everything else — `AT+DATASTAT?`,
> `AT+RXCHAN?`, `AT+FILTSTAT?`, `AT+RXREORD?`, `AT+HWMPSTAT?` — works on every
> build.

Commands are tagged:
**[op]** everyday operation · **[diag]** diagnosis · **[dev]** developer

## Identity and lifecycle

| Command | | Purpose |
|---|---|---|
| `AT` | [op] | Liveness. Answers `OK`. |
| `AT+VERSION?` | [op] | Firmware version, baked in from the release tag. |
| `AT+STATUS?` | [op] | Address on every surface, and the USB network counters since boot. `+USB: ... mounted=<0\|1> tx=<n> drop=<n>`: frames handed to the USB class driver (NCM: copied into a transfer block, not yet confirmed on the bus) and every frame dropped on the way. `+USBNET: tx_queued=<n> txq=<n>/16 txq_hw=<n> tx_stall_ms=<n> tx_busy_ms=<n> drop_full=<n> drop_nolink=<n> drop_nomem=<n> drop_bad=<n> \| rx=<n> rx_xfer=<n> rx_nomem=<n> rx_err=<n> rx_idle_ms=<n> \| kicks=<n>`: `tx_queued` frames lwIP handed over that the queue took; `txq` frames waiting for the TinyUSB task now, `txq_hw` the most ever; `tx_stall_ms` how long the oldest waiting frame has waited, 0 with none (over 1000: the host is not reading); `tx_busy_ms` how long the class driver has held frames with no IN transfer finishing, 0 when it holds none (over 1000: the host is not reading, even with `txq` at 0); dropped because the queue was full (`drop_full`), the host was detached or suspended, flushes on detach included but not frames already in the class driver (`drop_nolink`), no heap for the copy (`drop_nomem`), length 0 or over 1514 (`drop_bad`); `rx` frames from the host handed to lwIP, `rx_xfer` USB receive transfers (NCM blocks, one frame each under ECM; `rx` above it means the host packs blocks), `rx_nomem` no heap for the copy, `rx_err` lwIP refused (counted only with `CONFIG_ESP_NETIF_RECEIVE_REPORT_ERRORS`, which no build sets, so always 0), `rx_idle_ms` since the last frame from the host, 0 before the first (rising while the host pings: receive is stuck); `kicks` times lwIP woke the TinyUSB task. Measured on air 2026-10-03 ([Troubleshooting](Troubleshooting#usb-networking-stops-after-large-pings)). |
| `AT+RESET` | [op] | Reboot; leaves safe mode ([Troubleshooting](Troubleshooting#the-board-drops-off-usb)). |
| `AT+ERASE` | [op] | Wipe the `warthog` NVS namespace — **all** stored credentials and settings. |
| `AT+DLMODE` | [diag] | Drop into bootloader download mode over the wire, no BOOT button: the board re-enumerates as the ROM device (`303a:0009`). Flash it with `esptool --before no-reset --after watchdog-reset`, which then boots the new image ([Flashing](Flashing#reflashing-a-running-board)). Used by `tools/bench/flash.sh`. On the way in the HaLow chip is reset and loses its firmware, so the node goes off the air, and the board drops off USB 100 ms before a core reset that also resets its USB peripheral. An RTC watchdog returns the board to the app 1800 s after the command, timed on the boot's slow-clock calibration, unless a reset ends download mode first: esptool does not stop it on this USB-OTG port, so a session must end in a reset before it fires (download mode entered with the BOOT button has no limit). The return reads `reset=DLMODE` and is not a crash boot; after an esptool session that loaded its flasher stub and did not reset, it reads `reset=WDT` with `crash_boots=1`, since the stub clears `.noinit` (from the stub's addresses, not measured). The `WARTHOG_DEVLOOP` builds (every `warthog-mesh-*` env) enter the same way when the console is opened at 1200 baud. Measured on air on 2026-10-07 (`warthog-mesh-sae-swccmp-meshvif`, two OpenMANET 1.8.0 peers): both peers dropped the node at their 300 s poll, where an image without the chip reset kept both links `ESTAB` for as long as it stayed in download mode; a board no esptool session touched returned with `reset=DLMODE` and `crash_boots=0`, and with the limit built at 60 s it left download mode 60.9 and 61.1 s after the command; after a session esptool ended, 12 of 12 entries (8 `AT+DLMODE`, 4 at 1200 baud) showed the ROM within 1.1 s, and 7 of 7 without the USB reset never did. |
| `AT+CHIPRESTART`, `AT+CHIPRESTART?` | [dev] | `AT+CHIPRESTART` asks the umac event loop to fail the HaLow chip's next health check at once, so the chip restarts as after a real failure: TX pauses, its firmware is reloaded and what the node had in it goes back ([Mesh Mode](Mesh-Mode#chip-restarts)); `+ERR: chip not running (<status>)` before morselib is up or while its event loop is down or stopping, `+ERR: event queue full, try again (<status>)` while the loop's event queue is full; with the loop running but the driver stopped the loop drops the request after the `OK` (`dropped`). The chip also restarts on its own when a health check fails (every 90 s, and after bus errors). `?` answers `+CHIPRESTART: restarts=<n> forced=<n> dropped=<n> mesh=<n> \| sta=<n> stafail=<n> keys=<n> keyfail=<n> cmdfail=<n> \| retried=<n> pending=<n> \| last_ms=<n>`: `restarts` handled, `forced` of them by `AT+CHIPRESTART`, `dropped` requests the event loop dropped with the driver stopped, `mesh` after which the mesh had everything back as at the start (same interface type, nothing failed); `sta`, `keys`: station records and keys put back, `stafail`, `keyfail` those the chip refused; `cmdfail`: other restore commands that failed or that the chip refused otherwise than at the start; `retried`: station records and keys the mesh service tick put back after a restore failed them; `pending`: those still waiting (data and management frames the chip would seal under a missing key are dropped, `nokey` in `AT+DATASTAT?`); `last_ms`: how long the last restart took. A mesh restart still resets the board when the reload fails, the chip interface cannot come back at its id, the channel cannot be set, or `BSS_CONFIG` or `MESH_CONFIG` cannot be sent; in client mode morselib's own recovery runs. Measured on air on 2026-10-03 (`warthog-mesh-sae-meshvif`, `warthog-mesh-sae-swccmp-meshvif`): back in about 1.1 s (`last_ms`), `restarts=1 mesh=1 keyfail=0 cmdfail=0`, `keys=7` with chip keys and 1 on swccmp; USB and the peer links stayed up; 12 of 12 restarts in a soak on both, `health` at least 2356 bytes free of 4096 (`AT+STACKS?`). |

## Uplink and downstream configuration

Everything here persists in NVS and outranks the build-time default.

| Command | | Purpose |
|---|---|---|
| `AT+HALOW=<ssid>,<psk>` | [op] | HaLow station credentials. `AT+RESET` to apply. |
| `AT+HALOW?` | [op] | Current SSID; passphrase not echoed. |
| `AT+WIFIAP=<ssid>,<psk>,<chan>` | [op] | 2.4 GHz AP settings. |
| `AT+WIFIAP?` | [op] | Current AP SSID and channel; passphrase not echoed. |
| `AT+DNS=<ipv4>` | [op] | Resolver handed to USB and AP clients by DHCP. A lease the node itself takes (upstream, mesh or batman) never changes it; while the bridge runs (`AT+MESHBRIDGE=1`) the node serves no DHCP and hosts take the mesh DHCP server's resolver. Validated; malformed input is rejected without touching NVS. Persisted; `AT+RESET` applies it. |
| `AT+DNS?` | [op] | Current value. |
| `AT+MTU?` | [diag] | Interface MTU: `+MTU: halow=<n> usb=<n> ap=<n>`, then `+MTU: ip_reass=<n> ip_reass_drop=<n> ip_short_drop=<n>`: IPv4 datagrams reassembled and handed back to lwIP (fragments to any of the Warthog's addresses, in every mode, and fragments a tethered host sends out the HaLow side, before NAPT reads them), fragments or datagrams dropped there (a broadcast or multicast destination, a bad header, no heap for the copy, a first fragment too short for its ports, the tcpip mailbox full), and whole TCP, UDP or ICMP packets to the Warthog (also to 0.0.0.0 while HaLow has no address) or through NAPT dropped as shorter than their header (20, 8, 8 bytes), which NAPT would read and rewrite past their end, with UDP packets without their destination port wherever they go. Since boot. `ip_reass` and `ip_reass_drop` measured on air 2026-10-03; `ip_short_drop` host-tested ([Troubleshooting](Troubleshooting#large-packets-from-a-node-at-mtu-1460-go-unanswered-ip-fragments)). |

| `AT+MESHBRIDGE=<0\|1>` | [op] | L2 bridge mode: USB, the Wi-Fi AP and the mesh become ports of one lwIP bridge, so tethered hosts sit on the mesh segment with their own MACs and take addresses from the mesh's DHCP server — the fix for CoT and mDNS, whose payload addresses alias under NAT, against a peer whose mesh interface is a bridge port. `xx:xx:xx:xx:xx:xx`, hex in either case; anything else answers
`+ERR: usage: AT+BATO=<mac>` (or `AT+BATTG=<mac>`). Every listing is sent whole, in

chunk, and `(truncated)` now only ends a listing at an entry longer than a chunk.

Second, `+FILTSTAT: mgmt_nours=<n> last=<32 hex>` (mesh only): unicast management frames other than beacons whose addr1 is another station, counted but not dropped, and the first 16 octets of the last one (frame control, duration, addr1, addr2). A Protected one from a peer still reaches host CCMP where it is on, which counts it in `tried` and `micfail` (`AT+SWCCMP?`); an unprotected Block Ack request or teardown still acts on this node's Block Ack state with its sender. |

`delivered=` in `AT+DATASTAT?` counts every data frame handed to the network
stack, on every delivery path. (Older builds counted it on only one path, one
this build never takes, so it read 0 on a healthy link; that is fixed.) It is
the positive control for any receive experiment: if it is not climbing, the
link is not carrying data and no other counter means anything.

`AT+RXCHAN?` reports `rxdrop=<count> reason=<last>`. The count covers every
frame the receive path finished with other than an ordinary delivery, so it is
not a loss counter by itself; `reason` is the most recent cause:

| Reason | Meaning |
|---|---|
| 3 | Plaintext data on a keyed link (only EAPOL may arrive unprotected) |
| 4 | Protected, but the chip did not decrypt it (no key, or wrong key) |
| 5 | CCMP header unreadable, or a replayed packet number (the replay check) |
| 6 | Too short to hold the CCMP MIC |
| 7 / 8 | Fragment (More Fragments, or a fragment number) with a group receiver address (addr1) / our own broadcast relayed back |
| 9 | 4-address EAPOL addressed to us (unsupported) |
| 10 | EAPOL consumed locally — **not a loss** |
| 11 / 12 | Controlled port closed / no LLC ethertype |
| 13 / 15 | No receiving interface / no network-stack callback registered |
| 14 | Delivered via the legacy callback — **not a loss**; current builds deliver without touching `rxdrop` |
| 89 | Mesh data in a shape mac80211 drops: a group receiver address without From DS alone (3-address), or a unicast one that is not 4-address |
| 90 / 91 / 92 | Mesh Control truncated / could not be stripped / Address Extension truncated |
| 93 | Leaf: a mesh frame for another node, dropped because forwarding and bridge are both off |
| 94 | A 4-address frame for another node **without** Mesh Control — never relayable, dropped in every mode |
| 95 | SAE: a group frame the chip decrypted under anything but the transmitter's own MGTK at the transmitter's AID. On every build but `warthog-mesh-sae-meshvif` that is every one the chip decrypts: its one group key is this node's own TX MGTK, which every peer holds and none sends under, so the frame is forged in the transmitter's name. | `AT+CCMPKAT?` | [dev] | Result of the AES-CCM known-answer test run at startup. |
| `AT+CRYPTOHOST=<0\|1>` | [dev] | Move CCMP between chip and host. |
| `AT+CRYPTOHOST?` | [dev] | Current setting, read back from the chip. |
| `AT+SWCCMP=<0\|1>` | [dev] | Turn host software CCMP off or on; not persisted. Acts only on the builds compiled with it, `warthog-mesh-sae-swccmp`, `-swccmp-meshvif` and `-swccmp-on` (armed at boot on `-swccmp-on`, and by batman mode on all three). `AT+SWCCMP=0` is refused while batman runs (`+ERR: batman is running; host CCMP must stay on`): it would end all group RX from peers. |
| `AT+SWCCMP?` | [dev] | Two lines. First, host CCMP counters: `on`, `tried`, `ok` (decrypted and verified), `micfail`, `tx_ok`/`tx_fail`, `nokey` (no key for the frame's key id), `grpkey` (a unicast keyed with a group key, refused), `badhdr`, `short`, and the last `keyid` and AAD. Second, the last MIC failure: `+SWCCMP: fail len=<n> keyid=<k> pn=<12 hex> hdr=<64 hex>`, where `len` counts the CCMP header, ciphertext and MIC, `pn` is least significant octet first (PN 6 reads `060000000000`), and `hdr` is the first 32 octets of the frame from its frame control (addr1 at octet 4, addr2 at 10); all zero until a frame fails. Unicast data addressed to another station is dropped before host CCMP (`not_ours` in `AT+FILTSTAT?`), so it counts in neither `tried` nor `micfail`; on 2026-09-30, before that filter, the fail line held such a frame (addr1 a Linux node, addr2 another Warthog). A Protected unicast management frame addressed to another station is not dropped: if the chip hands those up (`mgmt_nours` in `AT+FILTSTAT?`), each counts in `tried` and `micfail` and replaces the fail line, whose addr1 then names that station. |
| `AT+KEYFP?` | [dev] | Fingerprint of the installed mesh keys. |
| `AT+KEYINST?` | [dev] | Key installation results per peer, the first eight installs: `aid`, `pw` (1 pairwise, 0 group), the key id asked for (`req`) and the chip's index (`hw`). On `warthog-mesh-sae-meshvif` each keyed peer's MGTK shows as `pw=0` at that peer's AID, beside our own at `aid=0`. |
| `AT+GTKSTAT?` | [dev] | Peers' MGTKs in the chip at their AIDs, as Linux installs them: `+GTKSTAT: per_sta=on\|on(pn0)\|off(at)\|off(build)\|off(sta_vif) inst=<n> fail=<n> del=<n> delfail=<n> tainted=<hex> rx_grp=<n> forged=<n> mgmt_gp=<n> fence=<n> taint=<n> mic_ok=<n> mic_bad=<n> mic_arm=<n> micdrop=<data>/<mgmt>` then one `[<peer's low 3 octets> aid=<n> id=<n> hw=<n>]` (or `[-]`) per peer slot. `per_sta=on` only on `warthog-mesh-sae-meshvif` running on a MESH chip VIF (`AT+MESHCFG?` `chip_vif=mesh(5)`) with `AT+GTKPERSTA=1`; `on(pn0)` the same with `=2`; `off(at)` with `=0`; `off(sta_vif)` is that build fallen back to a STA VIF, `off(build)` every other build, where peers' MGTKs stay host-only. `inst`/`fail`: a peer's MGTK installs the chip took and that failed (refused or no transport; that peer's group frames then stay `AT+RXCHAN?` reason 4); `del`/`delfail`: removals (`DISABLE_KEY`, when the peer leaves, a new key takes another index, an install fails or `AT+GTKPERSTA=0`, and the retry of a stale index before an install) the chip took and whose command failed; `tainted`: peer slots (bit per slot) where a refused removal may leave a stale key, whose group frames are all refused until a removal there succeeds or the chip boots; `rx_grp`: group data the chip opened under the sender's MGTK at its AID that passed the replay check; `forged`: group data the chip opened that was refused (reason 95, on every build); `mgmt_gp`: the same as `rx_grp` for group path selection (`mgmt gp chip` in `AT+MESHFWDSTAT?`); `fence`: of the refused, data and path selection read off the chip before the sender's current MGTK went in; `taint`: refused while tainted; `mic_ok`/`mic_bad`: of the fresh ones (past the replay check, which replays never reach), those whose MIC octets, as the chip left them, verify under the sender's MGTK, and those that do not; `mic_arm`: frame classes whose check a `mic_ok` has armed (1 data, 2 path selection, 3 both); `micdrop`: frames dropped for a `mic_bad` once armed (data, path selection). Unarmed, `mic_bad` drops nothing: `mic_ok` keeping pace with `rx_grp` + `mgmt_gp` shows the chip opened them under the sender's key and kept the MIC; `mic_bad` with `mic_arm=0` that it does not keep the MIC octets, or opened them under another key. On chip firmware 1.17.6 `mic_bad` counts every frame and `mic_ok` stays 0 (measured 2026-10-01), so the check never arms. |
| `AT+GTKPERSTA=<0\|1\|2>` / `AT+GTKPERSTA?` | [dev] | `warthog-mesh-sae-meshvif` only (no effect elsewhere): whether each peer's MGTK goes into the chip at its AID. `0`: no; every group frame the chip opens for a peer is refused at once, and within one service tick (about 2 s) every peer's MGTK is taken out of the chip (`del`): the behaviour measured before this existed. `1` (default): yes, each install at a fresh TX PN epoch. `2`: yes, at TX PN 0 as Linux installs it. Applies at once and persists (NVS); `?` answers `+GTKPERSTA: <live> stored=<nvs>`. `0`, `1` and `2` measured on air on 2026-10-01 (`2`: keys installed at PN 0, traffic passed). |
| `AT+REKEY=<n>` | [dev] | Re-push peer slot *n*'s own pairwise key to the chip: its AMPE MTK under SAE (with its MGTK at its AID on `warthog-mesh-sae-meshvif`), the built-in constant on a keyed non-SAE mesh. Nothing is installed on an open mesh, for a candidate AMPE has not keyed, or on the `-nochipkey`/`-swccmp` builds, which keep AMPE keys out of the chip. |
| `AT+REKEYSTAT?` | [dev] | Result of the last rekey: `done` counts keys actually installed; `aid` is the peer's AID, or 4294967295 when nothing went in. |

## Worked example: bringing up a mesh link

```
AT+MESHEN=1                      mesh instead of a station uplink
AT+MESHID=halowmesh              must match the peer exactly
AT+MESHPASS=<passphrase>         SAE builds only; must match the peer
AT+RESET                         the three above take effect on boot
AT+MESHSEC=0                     match an unencrypted peer
AT+MPMPEERS?                     confirm estab=1 and a non-zero plid
AT+HWMPSTAT?                     confirm preq_tx climbing (open mesh), parse_fail=0
AT+MPING=10.77.191.116,8         confirm data
```

If `AT+MPMPEERS?` shows `estab=1` but `AT+MPING` fails, the peer has no *path* to us —
see [Mesh Mode](Mesh-Mode#how-paths-work-and-why-it-matters).
