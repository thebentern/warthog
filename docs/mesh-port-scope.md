### Decision gate — read before Phase 3

Phases 3–6 (beaconing, PLINK peering, SAE, datapath) should **not** be built
until the Phase 2 diagnostic runs on hardware:

- **If the chip ACCEPTS the mesh VIF** → the firmware has a mesh path; Phases
  3–6 are worth building. First Phase-3 step: add `MORSE_CMD_ID_MESH_CONFIG`
  + `struct morse_cmd_req_mesh_config` to the fork's `morse_commands.h`
  (layout known from the GPL Linux driver's autogenerated header), add an
  `mmdrv_mesh_config()` wrapper, sequence SET_CHANNEL → BSS_CONFIG →
  MESH_CONFIG(START) → beaconing in `umac_mesh`.
- **If the chip REJECTS it** → the bundled firmware is STA/AP-only. No amount
  of host code makes it mesh. Options then: (a) ask Morse for a mesh-capable
  `mm6108.mbin`, (b) revisit the Linux-driver-port path from the original
  feasibility memo. Phases 3–6 as scoped here become moot.

Building Phase 3+ blind — on a firmware whose mesh support is unconfirmed —
would be writing thousands of lines that may never execute. Phase 2 is the
correct stopping point for hardware-free implementation.

### Phase 4e — first attempt; learned the architecture is different

Tried adding `wpa_supplicant_join_mesh(mesh_wpa_s, ssid)` to
`umac_supp_add_mesh_interface()` immediately after `add_iface`. The
hypothesis was: kick the PLINK state machine into life and let the hostap
event loop drive mesh_mpm.

**Crash on boot.** Stack from the panic:
```
Core 0 panic'ed (Interrupt wdt timeout on CPU0).
  gpio_set_level                                  ← spun, watchdog fired
  wlan_hal_gpio_init   (mmhal_wlan.c:48)          ← re-init GPIO from scratch
  mmhal_wlan_init      (mmhal_wlan.c:235)         ← re-init HAL
  mmint_morse_trns_start                          ← restart SPI transport
  mmint_mmdrv_init                                ← cold-init the chip driver
  mmint_umac_interface_add                        ← second ADD_INTERFACE call
  mmint_mmdrv_host_get_beacon                     ← incoming beacon RX
  mmint_umac_evt_dequeue                          ← umac task dispatching
```
The trace is unambiguous: `wpa_supplicant_join_mesh` succeeded synchronously
and queued a follow-on event. When the chip then RX'd its first mesh
beacon, the event loop processed `mmdrv_host_get_beacon` → which somehow
triggered `umac_interface_add(MESH)` *a second time* — and the chip was
already in mesh mode from our direct `mmdrv_add_if(MESH)` +
`mmdrv_mesh_config(START)` in Phase 3. The second `umac_interface_add` hit
the cold-init branch and tried to restart the entire SPI/GPIO HAL while
the chip was mid-operation. The GPIO re-init spun, INT_WDT fired, panic.

**The architecture lesson.** We have two mesh-setup paths in the firmware:

| Path | Chip setup | Driven by |
|---|---|---|
| Direct (Phase 3) | `mmdrv_add_if(MESH)` + `mmdrv_mesh_config(START)` | `umac_mesh_enable_mesh()` from `mmwlan_mesh_enable()` |
| Hostap (Phase 4e) | `wpa_supplicant_join_mesh` → `wpa_supplicant_mesh_init` → ... → `umac_interface_add(MESH)` | the supplicant event loop |

Both end up calling `umac_interface_add(MESH)`. They can't both run.
Calling `wpa_supplicant_join_mesh` triggers hostap's "set up the mesh
interface from scratch" code path, which assumes the chip is uninitialised.

**Right architecture: our direct umac path owns the chip; hostap mesh is a
passive PLINK state machine.** The supplicant context exists (Phase 4d's
`add_iface` worked), and it holds the ssid + driver_ops. But we don't ask
the supplicant to drive chip setup. Instead, when the chip RX's a mesh
peering action frame, we route it directly to `mesh_mpm_action_rx`. Hostap
mesh's state machine then runs PLINK (Open / Confirm / ESTABLISHED) and
emits action-frame replies via `.send_mlme` — which lands in the AP-share
`mmwpas_send_mlme` and goes back out the chip's existing mesh VIF.

Reverted the `wpa_supplicant_join_mesh` call from `supplicant_core_mesh.c`.
Kept everything else from Phase 4d (config + driver_ops registered,
`add_iface` still runs successfully). Smoke is back to its post-Phase-4d
state.

### Phase 4f — RX dispatch (the actual next step)

What needs wiring next, instead of `join_mesh`:

1. Identify the chip-side RX path that delivers mesh action frames to the
   umac event loop. In the AP path, action frames go through
   `umac_datapath_process_rx_action_frame` → `umac_supp_process_mgmt_frame`
   → AP's hostap handler. We need to add a mesh case that routes to
   `mesh_mpm_action_rx` instead of the AP handler.
2. Initialize hostap's mesh state machine WITHOUT going through
   `wpa_supplicant_join_mesh` — set up the bare minimum hostapd_iface /
   bss / `wpa_supplicant->ifmsh` that mesh_mpm needs to operate, while
   skipping the chip-setup path that crashed us.
3. Wire `wpa_mesh_notify_peer` (called by mesh_mpm on state transitions)
   into a real peer table behind `mmwlan_mesh_get_peer_count()`.

This is harder than Phase 4e looked. It's "selectively use parts of hostap
mesh" rather than "call its public entry point." The TX side
(`send_mlme`) is already wired; we just need to short-circuit init and
hook RX. Two-board verification needed to confirm peers actually establish.

  | Opcode | Value | Reach |
  |---|---|---|
  | `MORSE_CMD_ID_MESH_CONFIG` | `0x0039` | chip — what we use today |
  | `MORSE_CMD_ID_SET_MESH_CONFIG` | `0xA018` | Linux driver, netlink only |
  | `MORSE_CMD_ID_SET_MCBA_CONF` | `0xA019` | Linux driver, netlink only |
  | `MORSE_CMD_ID_DYNAMIC_PEERING_CONFIG` | `0xA020` | Linux driver, netlink only |

  The `0xA0xx` range is the Linux GPL driver's userspace command surface
  (nl80211 vendor commands) — those never reach the chip. There are **no
  mesh event IDs** in the upstream header at all. PLINK in the Linux mesh
  stack runs entirely in wpa_supplicant userspace — exactly the same place
  hostap mesh_mpm would run for us. The chip provides one primitive
  (beacon on/off via `MESH_CONFIG`) and nothing else. No subscription to
  opt into. Phase 4f host-side wiring is the only path.

  chip is configurably beaconing (it does this correctly) but received
  mesh frames don't surface through any path the host can tap with the
  current chip ABI.

### Phase 4 — wall reached

The remaining gap isn't host code (we wrote what's needed and it works)
— it's that **the chip ABI we know about doesn't route mesh peer frames
to the host**. To unblock, somebody needs one of:

- Documentation or source for the `mm6108.mbin` firmware that explains
  how received mesh frames are dispatched (probably non-public).
- An opcode found in newer GPL `morse_driver` versions that enables a
  mesh-RX subscription we're missing. Worth re-checking when MM releases
  driver updates.
- An interception point lower in the chip RX stack — i.e. hook
  `mmdrv_host_get_beacon` or similar pre-supplicant entry to capture
  mesh beacons + manually initiate PLINK from there. Bigger reimplementation
  (would duplicate parts of mesh_mpm in our umac layer).

None of those are within a single-session scope. Phase 4 is **paused at
a clearly-defined wall**: the host-side state machine is built and ready,
chip-side delivery is the open question.

The work landed in this branch is still valuable: chip beacons in mesh
mode (Phase 3) is a real bring-up milestone, the hostap layer being
selectively linkable into morselib is now a worked example, and the
passive `wpa_s->ifmsh` pattern is documented for whenever the chip-side
gap closes.

- **2026-05-25 — Diagnosed the chip-RX-routing gap.** Two boards beaconing
  on the same mesh_id produced zero `Mac EVT 0x____` (the umbrella event-
  channel diagnostic) AND zero hits at `umac_supp_process_mgmt_frame`
  (the mgmt-frame entry point we wired and instrumented). Tracing
  upstream surfaced the actual mechanism: in `umac_datapath_rx_frame_filter`
  every received frame is checked against `data->ops != NULL` and dropped
  with a WRN-level "Frame received before datapath configured" if NULL.
  In mesh mode `data->ops` IS NULL — there's no mesh analog of
  `umac_datapath_configure_ap_mode` (or `_sta_mode`). The chip is
  presumably delivering frames just fine; they never make it past this
  gate.

  Tried the obvious shortcut: install `datapath_ops_ap` from
  `umac_mesh_enable_mesh()`. Result was an immediate boot-loop crash
  inside `umac_ap_is_stad_paused` (NULL+0x108 dereference). Backtrace:

  ```
  #0  umac_ap_is_stad_paused      ← LoadProhibited
  #1  umac_ap_tx_dequeue_frame
  #2  umac_datapath_process_tx_frame
  #3  umac_datapath_process
  #4  umac_evt_dequeue
  ```

  The chip drives `umac_datapath_process_tx_frame` on its own (asking
  the host for the next TX frame — probably the mesh beacon template,
  since `mmdrv_host_get_beacon` already routes through `umac_ap_get_beacon`).
  AP ops dispatch TX to `umac_ap_*` functions that assume the AP STA
  table is populated. In mesh mode the STA table is empty and the
  lookup returns NULL.

  **Conclusion: AP ops cannot be shared with mesh.** To actually pass the
  RX filter without crashing the TX side, we'd need a complete
  `datapath_ops_mesh` table with all eleven function pointers implemented
  in a mesh-aware way:

  - `process_rx_mgmt_frame` — mesh-specific mgmt dispatch (action frames
    to `mesh_mpm_action_rx`, beacons to neighbour discovery)
  - `lookup_stad_by_peer_addr` — mesh-peer table lookup (we have nothing
    behind `mmwlan_mesh_get_peer_count` yet)
  - `lookup_stad_by_tx_dest_addr` — same, for outgoing frames
  - `lookup_stad_by_aid` — mesh peers aren't assigned AIDs the same way
    AP STAs are; need to figure out the mapping or stub
  - `set_stad_sleep_state`, `is_stad_tx_paused` — mesh peer state
  - `enqueue_tx_frame`, `dequeue_tx_frame` — mesh TX queue (4-address)
  - `construct_80211_data_header` — mesh 4-address header (different
    from AP's 3-address)
  - `get_sta_state`, `frames_allowed_pre_association` — peer state machine

  That's a full mesh datapath port — multiple weeks of focused work
  including building the peer table backing `mmwlan_mesh_get_peer_count`,
  implementing the 4-address frame construction (Phase 6 territory),
  and validating each function against the chip's expectations. Not
  practical for a single iteration session.

  chip beacons as mesh STA (Phase 3), supplicant context + ifmsh + bss +
  mconf + own_addr allocated (Phase 4a-4f-step3), action-frame SELF_PROTECTED

- **2026-05-25 — Final diagnostic: chip never asks host for beacon templates

  That closes the last host-side angle. The full picture of mesh mode
  from the host's perspective:

  | Observable | Mesh mode behaviour |
  |---|---|
  | Chip accepts config commands | ✅ all four — ADD_INTERFACE, SET_CHANNEL, BSS_CONFIG, MESH_CONFIG |
  | Chip reports "beaconing" | ✅ yes (the chip log says so) |
  | Chip calls `mmdrv_host_get_beacon` (host-built beacon template) | ❌ never — chip generates internally |
  | Chip delivers received frames via `mmdrv_host_process_rx_frame` | ❌ never — chip filters everything internally |
  | Chip emits events via `MORSE_CMD_ID_EVT_*` channel | ❌ never (verified via default-case `Mac EVT 0x____` log) |

  In mesh mode the chip is a fully closed loop. There is no host-callable
  RX path, no host-callable beacon-content path, and no event channel
  exposing peer activity. The Linux GPL driver works around this by
  having mac80211 + wpa_supplicant operate _alongside_ the chip with
  full ieee80211_hw integration — but the chip-firmware <-> embedded-host
  ABI exposed via morselib does not expose enough to drive mesh without
  that mac80211 layer.

- **2026-05-25 — Deep research follow-up: closure is partially wrong.**
  After the Phase 4 closure call above, did an extensive sweep across
  Morse Micro's public Linux driver (`MorseMicro/morse_driver` main,
  v1.17.9, May 2026), community forum threads, and the upstream
  `morse_commands.h` to compare the chip ABI surface exposed to the
  Linux driver vs. what `morsemicro/halow` 2.10.4-esp32-1 exposes to
  the embedded host. Key findings, in order of bite:

  1. **Direct quote, Morse Micro support forum** (thread "Sensor Mesh
     with Wi-Fi HaLow"):
     > "We don't support standalone mode (user running code directly)
     > on our MM6108 SoC… our microcontroller stack does not currently
     > support 802.11s-style mesh."

     This is the OFFICIAL position. The microcontroller-SDK gap is
     intentional, not an oversight. The recommended path Morse points
     people at is HaLowLink1 (their Linux box) or MT7628-based Linux
     dongles — not the ESP32 / morselib stack.

  2. **Same firmware binary as Linux.** There is exactly one
     `mm6108.mbin` (399 KB) in the `morsemicro/firmware` repo. The
     Linux driver, OpenWrt build, and our ESP32 port all load the
     same blob. There is a `mm6108-tlm.bin` (thin LMAC) variant but
     it is for high-station-count AP, NOT mesh. So **the chip
     firmware does support mesh** — the Linux driver drives it. The
     gap is purely on the morselib host side.

  3. **Missing chip-command wrappers in the embedded port:** the
     Linux driver's `command.h` exposes opcodes the embedded
     `morse_commands.h` doesn't:

     | Opcode | Linux name | Role |
     |---|---|---|
     | `0x003C` | `MCAST_FILTER` | multicast filter (mesh broadcast RX) |
     | `0x003D` | `BSS_BEACON_CONFIG` | enable beacon offload on a BSS |
     | `0x0053` | `BEACON_OFFLOAD` | upload beacon template + IE TLVs |
     | `0x0054` | `PROBE_RESPONSE_OFFLOAD` | probe response template |
     | `0xA018` | `SET_MESH_CONFIG` | driver-internal — stores mesh_id |
     | `0xA019` | `SET_MCBA_CONF` | mesh beacon collision avoidance |
     | `0xA020` | `DYNAMIC_PEERING_CONFIG` | RSSI-margin peer mgmt |

     `SET_MESH_CONFIG (0xA018)` is a driver-internal userspace→driver
     opcode — it stores the mesh_id in Linux driver RAM and triggers
     `cfg_mesh_bss()` which sends `MESH_CONFIG (0x0039)` to the chip.
     So `0x0039` IS the only mesh-specific chip opcode, and we
     already call it. The mesh_id never traverses the chip ABI.

  4. **The Linux mesh beacon model is push, not poll.** In the AP
     path, embedded morselib has a polled-beacon model: chip raises
     `MORSE_INT_BEACON_BASE_NUM + vif_id` IRQ, driver calls
     `mmdrv_host_get_beacon()` → `umac_ap_get_beacon()` which
     constructs from `umac_ap_data->config.head/tail`. This is set
     up by `mmdrv_start_beaconing(vif_id)` (driver.c:573), which is
     called from `umac_ap_start()` at `umac_ap.c:267`. **We never
     call `mmdrv_start_beaconing()` for mesh.** That alone could
     explain the chip's silence on the beacon callback path — the
     beacon IRQ is just not enabled for the mesh VIF.

  5. **Hidden generic-param knobs:** the embedded `morse_commands.h`
     exposes `MORSE_CMD_PARAM_ID_BEACON_OFFLOAD = 24` and
     `MORSE_CMD_PARAM_ID_PROBE_RESP_OFFLOAD = 25` as
     `GENERIC_PARAM (0x003E)` subcommands — never used by morselib
     anywhere. These are settable via the existing `mmdrv_set_param()`
     wrapper (just need to bypass the truncated internal `morse_param_id`
     enum which only includes 0–22). Setting these to 1 might tell
     the firmware to expect the push-template model.

  **Reframe of the closure.** Phase 4 is closed not because the chip
  firmware lacks mesh — it doesn't lack mesh. Phase 4 is closed
  because the morselib host stack lacks **at minimum**:

  - A call to `mmdrv_start_beaconing()` on the mesh VIF (1 line)
  - A mesh-aware `umac_ap_get_beacon()` substitute that returns
    a proper S1G mesh beacon (Mesh ID IE 0x72 + Mesh Configuration
    IE 0x71 + S1G Capabilities IE + RSN IE if SAE) instead of
    asserting on `data->config`
  - Possibly the `BEACON_OFFLOAD = 24` and/or
    `PROBE_RESP_OFFLOAD = 25` generic-param toggle
  - Possibly the `MCAST_FILTER (0x003C)` opcode wired up to admit
    broadcast mesh-control frames

  The cheapest experiment to discriminate "polled vs. pushed beacon
  model in mesh mode" is:

  1. Add `mmdrv_start_beaconing(mesh_vif_id)` after the existing
     `mmdrv_mesh_config(START)` call in `umac_mesh_enable_mesh()`.
  2. Guard `mmdrv_host_get_beacon()` to return NULL when
     `umac_data_get_ap(umacd) == NULL` (i.e. mesh mode) — keeps
     the existing diagnostic counter alive but avoids the AP-only
     assert in `umac_ap_get_beacon()`.
  3. Flash both boards. Watch for `mmdrv_host_get_beacon#1` in the
     log.

  Two outcomes:
  - **Counter fires.** The chip uses the polled model in mesh too;
    we just never enabled it. Next step is building a proper mesh
    beacon constructor (1–2 days of IE-builder work), then a
    sniffer check that the on-air beacon now contains Mesh ID IE.
  - **Counter stays at 0.** The chip's mesh firmware uses a different
    path (push template via `BEACON_OFFLOAD 0x0053`, or fully
    internal-and-empty). Then the next experiment is the param
    toggle + sending the missing `BEACON_OFFLOAD` opcode.

  Either way the closure verdict ("architecturally infeasible") was
  too strong. It's not infeasible — it's a defined unit of work, the
  size of which depends on which of the two outcomes the experiment
  reveals. The morse-support inquiry (`docs/morse-support-inquiry.md`)
  has been refined to ask the specific questions whose answers gate
  this work; sending it costs nothing and may save days of reverse-
  engineering.

  - **4e — peer events.** Wire `wpa_mesh_notify_peer` / peer-ESTABLISHED to
    `mmwlan_mesh_peer_event_cb` + a real peer table behind
    `mmwlan_mesh_get_peer_count()`. *Needs 2 boards to runtime-verify.*

  4a–4c can land and build-verify before the second board arrives; 4d–4e are
  where two nodes exchanging PLINK frames is mandatory.
- **Phase 5 — SAE.** Mesh secure peering via the vendored hostap SAE +
  mbedTLS. Only needed for encrypted mesh; open mesh peers without it.
- **Phase 6 — datapath.** Mesh data frames (4-address) in/out, so peers pass
  IP traffic. Validate with ping between two peers.

## TL;DR

We do **not** need to port the Linux `morse_driver` from scratch. The
`morsemicro/halow@2.10.4-esp32-1` ESP component already ships:

- **AP mode** as a fully exposed public API (`mmwlan_ap_enable`, `mmwlan_ap_disable`,
  `mmwlan_ap_get_bssid`, `mmwlan_ap_get_sta_status`, etc.). The `softap` and
  `dual_if` examples in the component prove it works on ESP32.
- **morselib as source** (not just precompiled binaries). The `umac/` directory
  contains the Upper MAC layer for STA + AP; we can add new modes there.
- **Full hostap `mesh.c` / `mesh_mpm.c` / `mesh_rsn.c`** in the vendored hostap
  component — that's the wpa_supplicant 802.11s peering state machine, already
  on disk.

The gap is narrower than the original memo described: we need a new
`umac/mesh/` source set in morselib + an `mmwlan_mesh_enable()` public API,
wired into the existing chip command dispatcher and the already-vendored
hostap mesh layer.

## What "peer mode" actually means here

We're splitting the original "build our own peer mode" ask into two distinct
products:

| Goal | Status | Path |
|---|---|---|
| AP-relay broadcast (one Warthog hosts an AP, others associate as STAs, broadcasts relay through AP) | **Available now** — use `mmwlan_ap_enable` + `mmwlan_sta_enable` on different nodes. The `dual_if` example demonstrates concurrent STA+AP. | Configure in `main/`, no new code in the driver. |
| AP-less peer mesh (every node is a peer, multi-hop forwarding, no infrastructure node) | **The actual gap.** Not in the public API; `umac/mesh/` doesn't exist. | This branch. |

If the use case is satisfied by AP-relay, this entire branch is unnecessary —
ship Warthog as planned with a Phase-3 "self-AP" option that lets any node
elect itself as the mesh portal. AP-less peer-to-peer is what `mesh-support`
targets.

## What's in the component (chip ABI exposure)

The chip firmware blob (`mm6108.mbin`) already accepts mesh opcodes — confirmed
by reading the autogenerated `morse_commands.h` from the GPL Linux driver
(`MorseMicro/morse_driver`, `morse_commands.h` semver 56.17.0):

```c
enum morse_cmd_interface_type {
    MORSE_CMD_INTERFACE_TYPE_STA   = 1,
    MORSE_CMD_INTERFACE_TYPE_AP    = 2,
    MORSE_CMD_INTERFACE_TYPE_MON   = 3,
    MORSE_CMD_INTERFACE_TYPE_ADHOC = 4,
    MORSE_CMD_INTERFACE_TYPE_MESH  = 5,
};
```

Mesh-relevant opcodes the chip understands:
- `MORSE_CMD_ID_ADD_INTERFACE` (0x0004) with `type = MESH`
- `MORSE_CMD_ID_MESH_CONFIG` (0x0039) — start/stop beaconing, MBCA params
- `MORSE_CMD_ID_BSS_BEACON_CONFIG` (0x003D) — beacon template + IEs
- `MORSE_CMD_ID_SET_OFFSET_TSF` (0x003A) — mesh neighbor TSF sync
- `MORSE_CMD_ID_INSTALL_KEY` (0x000A) — for mesh SAE PTK/GTK

These all exist in the chip firmware. **We're not asking the silicon to do
anything new** — we're asking the host driver to send commands the firmware
already accepts.

## Risks specific to this approach

- **Internal API exposure.** Morse may not export the umac event-loop hooks
  we need from the registry component. If they don't, we go to fork mode.
- **Chip firmware mesh path validation.** The opcodes exist per `morse_commands.h`,
  but we haven't seen them exercised. Could discover bugs the Linux driver also
  hits; Morse may or may not have fixed them in the ESP32-targeted firmware.
- **Apache-2.0 (registry component) + GPL (hostap mesh code).** The hostap
  mesh files are already in the registry component under Apache-2.0 dual
  license arrangement — verify by reading their LICENSES/ dir. If hostap is
  in GPL mode there, our derivative is GPL.
- **No mesh11sd-equivalent for daemon-level orchestration.** Linux runs a
  userspace daemon (`mesh11sd`) to coordinate beacon timing, neighbor lists,
  blacklisting. We'd need either an in-firmware equivalent or to accept its
  absence (simpler peering, less robust).
- **mbedTLS SAE support.** Verify ESP-IDF's mbedTLS includes the elliptic-curve
  primitives SAE needs. Likely yes (it's a standard Suite-B operation), but
  needs confirmation.

## Out of scope for this branch

- IBSS / ad-hoc mode. The chip supports it but mesh is the actual user-facing
  requirement; IBSS only makes sense as a stepping stone.
- Monitor mode. Useful for debugging but not for the peer-mode product.
- Multi-hop routing (HWMP / RANN). The first milestone is two-peer mesh; multi-
  hop is a follow-up branch.
- Mesh portal mode (peer + AP concurrent on the same radio). The Linux driver
  does this via `morse_mesh11sd`; we'd replicate after single-peer works.

Two ESP32+HaLow boards, both flashed with this branch's Warthog firmware, both

3. PLINK handshake completes, peer state = ESTABLISHED.

That's the demo. From there, multi-peer + multi-hop are follow-up work in

## Phase 4f Final Report — Mesh Chip-Firmware Behavior (Steps 1–26)

After 26 documented iterations (steps 4f-1 through 4f-26) progressively
matching the Linux morse_driver mesh bring-up byte-for-byte at the chip
command interface, **the MM6108 firmware version `rel_1_17_6_2026_Feb_23`
does not exhibit observable mesh activity beyond the initial handshake.**

### What works (chip-level)

- `MORSE_CMD_ID_ADD_INTERFACE (0x0004)` with type=MESH accepts and returns
  a valid VIF id.
- `MORSE_CMD_ID_SET_CHANNEL (0x0001)` configures the operating channel.
- `MORSE_CMD_ID_BSS_CONFIG (0x0006)` with mesh CSSID accepts.
- `MORSE_CMD_ID_BSSID_SET (0x0052)` accepts both own_addr and broadcast
  values (step 26 confirmed values are interchangeable from a behavior
  standpoint).
- `MORSE_CMD_ID_SET_QOS_PARAMS (0x0011)` accepts 4 AC entries.
- `MORSE_CMD_ID_BSS_BEACON_CONFIG (0x003D)` enable=true accepts.
- `MORSE_CMD_ID_MESH_CONFIG (0x0039)` opcode=START with mbca_config=0x01
  (TBTT_SEL_ENABLE) OR 0x00 (MBCA disabled) both accepted (step 25).
- The beacon-template polled-callback fires exactly **once** at startup
  (`mmdrv_host_get_beacon#1`).

### What does NOT happen

- **`mmdrv_host_get_beacon#2` never fires.** Chip beacon IRQ at offset
  `MORSE_INT_BEACON_BASE_NUM(17) + vif_id` does not re-trigger after
  the initial manual notify (`mmdrv_start_beaconing` does
  `driver_task_notify_event` directly). Step 24 instrumentation in
  `morse_beacon_work_` confirms beacon_irq counter stays at 1.
- **`mmdrv_host_process_tx_status` never fires.** No TX completion
  notifications for any frames — meaning either the chip is not
  transmitting, or mesh-mode TX_STATUS events bypass the host
  notification path entirely (no way to disambiguate without sniffer).
- **`mmdrv_host_process_rx_frame` never fires.** Zero frames cross the
  chip→host shim despite both boards being configured for the same mesh
  on the same channel.
- **`Mac EVT 0x____` unknown events never log.** Step 21 instrumentation
  raised the unknown-event log path to ERR level — no unknown chip events
  are emitted at any point in mesh mode.

### Things tried that didn't help

| Step | Change | Result |
|------|--------|--------|
| 15 | `BSSID_SET(own_addr)` | Accepted; no change in RX |
| 16 | `SCAN_CONFIG(enable=true)` | Rejected with -17 (some chip-internal error) |
| 17 | `BSS_BEACON_CONFIG(enable=true)` | Accepted; chip silent |
| 18 | MESH_CONFIG with full MBCA defaults | Accepted; chip silent |
| 19 | Push 4 default QoS queue configs first | Accepted; chip silent |
| 20 | TX_STATUS diagnostic | Confirmed: zero TX completions ever |
| 21 | Unknown-event diagnostic | Confirmed: zero chip events ever |
| 22 | `enable_beaconing=false` (pure listen) | Confirmed: zero RX even without TX |
| 23 | S1G beacon format (FC 0x001C vs 0x80) | Beacon built correctly; chip silent |
| 24 | TX-frame + beacon-IRQ counter diagnostics | Confirmed: chip beacon IRQ fires exactly once |
| 25 | MBCA disabled (`mbca_config=0`) | Confirmed: MBCA not the gating factor |
| 26 | `BSSID_SET(broadcast)` | Confirmed: BSSID value doesn't affect chip behavior |

### Root cause hypothesis

The firmware blob `mm6108.mbin` (`rel_1_17_6_2026_Feb_23`) contains the
strings `mesh_tbtt` and `mesh_delayed_start` (visible via `strings` on
the binary), indicating SOME mesh-aware code is compiled in. But:

- It accepts the chip commands as a no-op (returns success but doesn't
  start the mesh state machine), OR
- It requires additional commands (e.g., `MORSE_CMD_ID_DYNAMIC_PEERING_CONFIG
  0xA020` or a firmware-private opcode) we haven't discovered, OR
- It has a known-broken implementation that the Linux driver works around
  via host-side state (mac80211 mesh + mesh_mpm) that we've ported but is
  fundamentally blocked by the chip's TX/RX behavior.

The Linux driver's mesh code path (verified against `/tmp/morse_driver/mac.c`
+ `command.c` + `mesh.c`) is exactly what we send to the chip. The
behavioral divergence must be in firmware between MM6108 builds Morse
ships publicly (limited) vs. internally (mesh-functional).

### Possible paths forward (not pursued in 4f)

1. **Wait for a newer chip firmware.** The current public release
   (`rel_1_17_6_2026_Feb_23`) appears to be the most recent. If Morse
   eventually publishes a release with full mesh support, retry.
2. **Use mesh-beaconless mode**: implement a host-side timer that
   periodically sends broadcast probe requests with the Mesh ID IE.
   Linux uses this exact mechanism when `mesh_beaconless_mode=true`.
   Probe-request RX may bypass whatever chip-internal filter blocks
   beacon RX in mesh mode. (Phase 5 candidate; would require chip TX
   to actually work for management frames.)
3. **Open an issue with Morse Micro support** documenting steps 1-26
   and asking for: (a) confirmation that firmware `rel_1_17_6_2026_Feb_23`
   supports mesh on MM6108, (b) the missing chip command(s) if any,
   (c) a firmware build with mesh enabled if a separate variant exists.
   The full bring-up sequence we send is documented in
   `docs/morse-support-inquiry.md`.
4. **Pivot to a non-mesh peer-to-peer model**: HaLow STA-to-AP+STA
   bridging (multiple STAs associating to a common AP that acts as a
   hub). Less elegant than mesh but the chip already supports it.

### Code state at end of Phase 4f

The mesh bring-up sequence in `umac_mesh_enable_mesh()` sends every chip
command the Linux driver sends, in the Linux order. The instrumentation
counters (mmdrv_host_get_beacon, beacon_irq, mmdrv_tx_frame, Mac EVT,
mmdrv_host_process_rx_frame, mmdrv_host_process_tx_status) all stay at
ERR level so any change in chip behavior surfaces immediately.

The hostap mesh path is wired and `passive_init_ifmsh` succeeds (mesh_mpm
has hapd + mconf + own_addr), so the moment chip-level RX starts working,
the host stack is ready to handle PLINK frames.

The S1G beacon constructor in `umac_mesh_beacon.c` produces a properly-
formatted S1G beacon (FC 0x001C, fixed 15B header, Mesh ID IE 114, Mesh
Configuration IE 113, S1G Beacon Compatibility IE 213, S1G Capabilities
IE 217, S1G Operation IE 232, S1G Short Beacon Interval IE 214) — ready
to drop in once chip-side mesh becomes functional.

## Phase 4f-step27–31 follow-up — Chip TX confirmed; RX is the blocker

After the first Phase 4f Final Report (steps 1–26), four more iterations
produced a critical breakthrough.

### Step 27 — reordered chip commands to match Linux exactly

Linux fires its mesh chip commands in the order:
`QoS×4 → BSS_BEACON_CONFIG → MESH_CONFIG(START) → BSSID_SET → BSS_CONFIG`.
Our embedded port previously sent them backwards. Reordering matched Linux
exactly, but chip behavior was unchanged. Order isn't the issue.

### Step 28 — enabled NDP probe support for the mesh VIF

Linux unconditionally calls `morse_ndp_probe_req_resp_init` for all AP-type
interfaces (including mesh) via `morse_mac_vif_init_ap`. Our embedded port
only enabled it for SCAN-type interfaces. Adding `mmdrv_set_ndp_probe(vif_id,
true)` (chip opcode `MORSE_CMD_ID_SET_NDP_PROBE_SUPPORT = 0x800C`) — chip
accepted, behavior unchanged.

### Step 29 — manual probe-request submission to test chip TX path

Before adding a periodic probe loop, verified that the chip TX path is
functional in mesh mode by hand-building a broadcast probe request (with
mesh_id as SSID) and calling `mmdrv_tx_frame` once during mesh enable.

**Result:**
- `mmdrv_tx_frame#1: is_mgmt=1 tid=7 (total mgmt=1)` — submitted to chip ✓
- `mmdrv_host_process_tx_status#1: chip TX completion` — chip transmitted ✓

**Chip TX works in mesh mode.** TX_STATUS firing means the chip put the
frame on-air.

### Step 30 — periodic 2s probe-request burst (mesh_beaconless mode equiv)

Added a FreeRTOS task that calls the new `mmwlan_mesh_tx_broadcast_probe()`
public API every 2 seconds, mimicking Linux's `mesh_beaconless_mode` peer-
discovery pattern (Linux uses this when chip beacon timer is unreliable).

Initially the burst task's "submitted" logs appeared but the chip-side
`mmdrv_tx_frame#N` counter stayed at 1, suggesting the probes weren't
reaching the chip.

### Step 31 — found the actual blocker (MMLOG silent-drop from non-umac tasks)

After adding ESP_LOGW alongside the existing MMLOG_ERR diagnostics, the
truth surfaced:

**MMLOG_ERR (and its underlying `mmosal_printf`) silently drops messages
when called from non-umac task contexts.** ESP_LOGW from the same
context works fine.

With ESP_LOGW in place:
```
W (40904) warthog.mesh:  probe_burst#20: pre-call mmwlan_mesh_tx_broadcast_probe
W (40904) mmwlan_mesh:   @@ wrapper #20 entered
W (40905) umac_mesh:     tx_broadcast_probe#20: mmdrv_tx_frame returned 0
                         (vif=0 ssid_len=17 probe=0x3fcc74d4)
W (40906) mmwlan_mesh:   @@ wrapper #20 umac returned 0
W (40906) warthog.mesh:  probe_burst#20: submitted ret=0
```

Each burst:
- Builds the probe-req mmpkt correctly (probe ptr non-NULL)
- Calls mmdrv_tx_frame which returns 0 (chip accepted)
- Repeats successfully every 2 seconds, indefinitely

So our embedded port **is** transmitting broadcast probe requests every
2s, with mesh_id as SSID, addr3=broadcast, on the configured mesh channel.

### What still doesn't work

Even with 40+ probes TXed by each board over 80+ seconds, **neither board's
chip→host RX path fires** (`mmdrv_host_process_rx_frame#N` stays at 0 on
both, despite that diagnostic being placed at the absolute earliest point
in the host RX stack).

The only remaining bottleneck is the **chip's RX path for mesh mode**.
The chip TXes our probes (TX_STATUS confirms transmission), but the
peer's chip either:
1. Doesn't receive them due to an RF / channel issue we can't see, OR
2. Receives them but its RX filter discards them before delivering to
   the host (mesh-mode RX filter is restrictive about Addr3 / BSSID).

Without a sniffer to confirm on-air activity, we can't distinguish (1)
vs (2). Both boards are on the same hub a few cm apart, so RF range is
not the issue.

### What we can conclude

The chip's mesh-mode RX behavior is restrictive in a way that's not
configurable via any chip command we've discovered through the Linux
GPL driver source. The fix likely lives in firmware (a different
build with mesh RX enabled, or a chip-internal flag we don't know
about). The codebase is in a state where mesh would Just Work the
moment the chip starts delivering peer RX frames — hostap mesh_mpm
is loaded, the supplicant has the mesh interface up, and the periodic
probe-request loop is running.

### Diagnostic infrastructure improvements

- **ESP_LOGW from morselib** is reliable from any FreeRTOS task. The
  `MMLOG_*` family relies on `mmosal_printf` → `vprintf` which silently
  drops output from non-umac contexts (separate ESP-IDF/morselib
  interaction bug worth a separate ticket).
- Counters added in this round:
  - `mmwlan_mesh_tx_broadcast_probe wrapper #N`
  - `umac_mesh tx_broadcast_probe #N`
  - `warthog.mesh probe_burst #N` (in main/mesh.c)
- The `s_mesh_umacd` / `s_mesh_vif_id` / `s_mesh_own_addr` cached state
  is reused by every burst — no fresh `umac_data` lookup per call.

## Phase 4g — Full Linux driver port feasibility study

After Phase 4f (31 chip-command iterations) established that chip TX works
in mesh mode but chip RX does not deliver foreign-BSSID frames to host,
the natural question is: **can we port the entire Linux morse_driver +
mac80211 to ESP32-S3 instead?**

Two parallel deep-dive investigations produced quantitative answers.

### Linux driver scope (cloc-measured)

**Total: 44,341 LOC across 128 files** in `/tmp/morse_driver/` (v1.17.9).
Breakdown by subsystem:

| Subsystem | LOC | Mesh-relevant? |
|---|---:|---|
| `mac.c` + `wiphy.c` (mac80211/cfg80211 upper layer) | 7,404 | YES — 49 mesh refs |
| `mesh.c` + `mesh.h` (driver-side mesh glue) | 592 | YES (entire file) |
| `dot11ah/` (S1G ↔ 11n header transform) | 5,776 | Partial — could be lifted standalone |
| Command/event protocol + `morse_commands.h` | 4,365 | Partial — ~26 mesh-touched lines |
| TX/RX feature handlers (twt, raw, hw_scan, beacon, pv1, …) | 8,549 | Mostly NOT mesh |
| Bus drivers (sdio + spi + usb) | 3,019 | NO (pure chip mgmt) |
| Datapath (skbq + pageset + pager_hw + yaps) | 3,987 | NO |
| Firmware load / chip init | 3,336 | NO |
| Rate control + misc | 5,482 | NO |

**Pure chip-management subtotal: ~10,342 LOC**. Everything else depends on
mac80211 to varying degrees.

### mac80211 dependency surface

The driver references **159 unique `ieee80211_*` symbols**, of which:

- ~70 are header-only struct types (could be replicated by header copy)
- ~50 are inline bit-check helpers (header-only)
- **~39 are real mac80211 FRAMEWORK calls** that resolve into
  `net/mac80211/*.o`

The driver implements **39 callbacks in `struct ieee80211_ops mors_ops`**
(mac.c:5601) — `tx`, `start`, `stop`, `add_interface`, `remove_interface`,
`config`, `bss_info_changed`, `prepare_multicast`, `configure_filter`,
`sw_scan_start/complete`, `conf_tx`, `sta_state`, `ampdu_action`,
`set_key`, `hw_scan`, `cancel_hw_scan`, `sched_scan_start/stop`, four
`*_vif_chanctx` ops, etc.

The driver uses **69 distinct `<linux/*>` and `<net/*>` kernel headers**
(workqueue, RCU, rtnl_lock, sock_buff, devcoredump, debugfs, MMC/SDIO,
SPI, USB, regmap, …) and contains **139 `KERNEL_VERSION()` conditionals**
(mac.c alone has 39) — even on Linux it's a moving target across kernel
releases.

### mac80211 mesh itself

`net/mac80211/mesh*.c` (mesh.c, mesh_hwmp.c, mesh_pathtbl.c, mesh_plink.c,
mesh_sync.c, mesh_ps.c) is **~7–10k LOC** but deeply intertwined with the
rest of mac80211: sta_info, IBSS, chanctx, TXQ, key infrastructure,
cfg80211 (NL80211 socket layer + chandef + regdomain), Linux skb / netdev
/ workqueue / timer / sock infrastructure. **Mesh cannot be lifted in
isolation.**

### Firmware variant analysis

Morse Micro chip firmware has THREE variants per chip family:

| Suffix | Mode | Where MAC code lives | Mesh support |
|---|---|---|---|
| (no suffix) | mac80211 softmac | host (mac80211) | YES via Linux mac80211 mesh |
| `-tlm` | thin LMAC | host (mac80211 + extra) | YES via Linux mac80211 mesh |
| `-flm` | full MAC | chip firmware | NO (STA-only per OpenWrt doc) |

**For MM6108 specifically, only the first two are published publicly.**
The driver's MM6108 path (`mm610x_get_fw_path`, mm6108.c) advertises only:
- `morse/mm6108.bin` (default mac80211 softmac)
- `morse/mm6108-tlm.bin` (thin LMAC)
- `morse/mm6108-vst.bin` (virtual STA test mode — binary not published)

**There is no `mm6108-flm.bin` advertised or published.** The morselib SDK
ships `mm6108.mbin` which is a different binary entirely (MMFW TLV
container w/ deflate, ~400KB vs Linux ELF ~480KB). This SDK firmware
appears to be a custom fullmac build for embedded use; it contains
`mesh_tbtt` + `mesh_delayed_start` symbol strings (so SOME mesh code is
present), but Phase 4f-step31 confirms its chip-side RX path does not
deliver foreign-BSSID mgmt frames to host.

### Bottom-line answer to "can we implement the entire Linux driver"

**No, not feasible within Warthog scope.** Concretely:

1. **~100k LOC of GPL Linux-kernel C** (44k driver + 50k mac80211) that
   assumes Linux runtime (workqueue, RCU, rtnl_lock, skbuff, debugfs,
   …). Multi-engineer-year port effort.

2. **GPL-2.0-or-later license**: would force Warthog into GPL too if
   statically linked — incompatible with the project's open-source-
   permissive goals.

3. **Chip firmware mismatch**: even if the host driver were ported, it
   expects the Linux ELF firmware (`mm6108.bin` or `mm6108-tlm.bin`),
   not the SDK's MMFW format. The Linux and SDK firmwares are
   **different builds**, not just different containers — the SDK
   fullmac firmware is 600-700KB after decompression (more chip-side
   MAC code), the Linux softmac firmware is ~480KB (less). No tool
   exists to convert one to the other; you'd need Morse Micro to
   build a mesh-capable MMFW.

4. **mac80211 mesh is not liftable in isolation** — it has ~50 internal
   mac80211 dependencies (sta_info, chanctx, TXQ, key, MLME, scan). The
   only liftable subsystem is `dot11ah/` (~5,800 LOC, would be 3-5k LOC
   after de-Linux-izing) — but that doesn't help with the chip RX
   blocker, since `dot11ah` is a frame-format transformer, not a chip-
   command extender.

### Realistic forward paths

**Path A: Get a mesh-capable MMFW from Morse Micro support.** The chip's
mesh code paths exist (the `mesh_tbtt` task is in our current firmware),
the chip TX works (Phase 4f-step29 confirmed), the only missing piece
is RX-side configuration. This is one support ticket away from a
working mesh.

**Path B: Get a redistributable MM6108 thin-LMAC blob in MMFW format
from Morse Micro.** Then port just enough of the Linux driver to drive
the thin-LMAC chip path — narrower scope than full driver+mac80211.
Probably still ~20k LOC of port effort and requires Morse cooperation
on firmware redistribution license.

**Path C: Switch to a different HaLow chip with public mesh support.**
The MM8108 has more firmware variants public including fullmac with
mesh, but our hardware (Seeed XIAO HaLow add-on) is MM6108-based.

**Path D: Use the host-side mesh-beaconless probe loop (already in
warthog as of step 30) and write a Morse-Micro-specific RX path that
bypasses the chip's filter** — would require chip firmware help we
don't have, see Path A.

**Path E: Accept current state.** HaLow STA mode works end-to-end on
this hardware. Mesh is gracefully degraded — chip accepts every command
in the Linux sequence, beacon template is delivered (S1G fmt), probe
requests TX continuously (mesh_beaconless equivalent), and the entire
hostap mesh_mpm + supplicant stack is loaded waiting for peer RX. The
moment Morse Micro provides the chip-config or firmware to open mesh
RX, peering should immediately succeed.

### Recommendation

**Path E + Path A in parallel.** The codebase is in a "ready to peer" state
— ship the STA-only release as Warthog v0.x, file a Morse support ticket
with `docs/morse-support-inquiry.md`, and integrate mesh activation as a
v0.(x+1) feature once Morse provides the missing piece.

## Phase 4i — Firmware reverse engineering breakthrough

After exhausting host-side experimentation (Phase 4f steps 1-33) and
documenting why a full Linux driver port is infeasible without firmware
cooperation (Phase 4g), Phase 4i did the next thing the user asked:
**reverse engineer the chip firmware itself.**

### Tools used

- `xxd` + `strings` + Python: extract MMFW TLV container
- `objcopy` (riscv32-esp-elf from PlatformIO toolchain): extract ELF sections
- `cmp -l`: byte-level diff between firmware variants
- Custom `mmfw_extract.py` and `elf_to_mmfw.py` in `scripts/firmware/`

### What we found

**The SDK MMFW `mm6108.mbin` and the public Linux ELFs (`mm6108.bin` and
`mm6108-tlm.bin`) all load to the same 9 chip memory regions at identical
load addresses.** Differences:

| Region | SDK 1.17.6 vs Linux softmac 1.17.9 bytes diff | vs Linux thin-LMAC 1.17.9 |
|---|---:|---:|
| host_imem (96KB)   | 54187 (55%) | 89387 (91%) |
| host_dmem (8KB)    | 178 (2%) | 4025 (50%) |
| mac_imem (155KB)   | 136232 (88%) | 128951 (88%) |
| mac_rodmem (4KB)   | 513 (12%) | 2190 (52%) |
| mac_dmem (21KB)    | 457 (2%) | 570 (3%) |
| uphy_imem (64KB)   | 40118 (62%) | 40118 (62%) |
| uphy_dmem (14KB)   | 32 (0.2%) | 31 (0.2%) |
| lphy_imem (28KB)   | 18708 (65%) | 18708 (65%) |
| lphy_dmem (5KB)    | 23 (0.4%) | 22 (0.4%) |

**Most striking finding:** `mac_rodmem` strings are byte-for-byte
identical across all three variants. Same FreeRTOS task names
(`mesh_tbtt`, `mesh_delayed_start`, `beacon`, `con_loss`, `ap_ps_rem_awake`,
`ps_wup`, `Qkkbal`, `Tmr Svc`), same trap/assert format strings, same
"Unsupported frame to TX. Frame control: 0x%04x" format string.

The MAC firmware code is the SAME across SDK and Linux variants —
just different builds (Feb 2026 vs Apr 2026).

### Live test on hardware (2026-05-26)

Wrote `scripts/firmware/elf_to_mmfw.py` that re-wraps a Linux ELF
firmware into MMFW TLV format. Successfully tested on both boards:

1. `mm6108_softmac_1_17_9.mbin` (Linux mac80211-softmac variant, 2 months
   newer than SDK) — **booted and ran normally**. Mesh setup commands
   accepted, beacon IRQ fires once, host-driven probe-request loop
   continued, chip RX behavior **unchanged from SDK** (zero peer frames
   reach host).
2. `mm6108_tlm_1_17_9.mbin` (Linux thin-LMAC variant, documented as
   "chip permissive RX, host does all MAC") — **booted and ran normally**.
   Mesh behavior **unchanged** — same chip silence on peer frames.

### Implications (definitive)

**The firmware is NOT the gate.** All three variants exhibit identical
chip-RX-blocked behavior in mesh mode. The Linux firmwares — designed
to work with mac80211 + the Linux driver — STILL block mesh peer
frames when driven by morselib.

**The gate is in morselib's host-side init/handshake sequence.** Somewhere
in `mmdrv_init` → `mmhalow_init` → the first few commands sent to the chip,
morselib transmits a config signal that locks the chip into "fullmac
restrictive RX" mode regardless of which firmware blob was loaded.

The Linux driver doesn't send that signal. Hence Linux mac80211 mesh
works with the same firmware that we can't get mesh RX out of.

### Forward path

The chip is now a glass box. We:
1. Know what's inside the firmware (regions, code/data layout, task
   names, format strings)
2. Can swap firmware variants at will (`scripts/firmware/elf_to_mmfw.py`)
3. Can extract and analyze segments (`scripts/firmware/mmfw_extract.py`)
4. Have proven the firmware is identical between SDK and Linux in MAC code

**Next investigation step would be:** trace the exact byte sequence
morselib's `mmdrv_init` sends to the chip BEFORE we do anything mesh-
related. Specifically the first ~10 chip commands. One of them is
sending "I am fullmac, restrict RX." Replacing/inhibiting that one
command should make the same chip accept foreign mesh frames.

That requires bus-level packet capture between morselib and the chip
(SPI sniffer or instrumentation in morselib's `morse_cmd_tx`) — which
is the next session's work.

## Phase 4j — `morse_cmd_tx` instrumentation: the boot-init command audit

Added an ERR-level capture inside `morse_cmd_tx` that logged opcode +
vif_id + payload length + 16-byte GENERIC_PARAM payload for every chip
command sent from boot. Then reverted (the printf overhead on USB-CDC was
hitting the ESP-IDF interrupt-watchdog deadline). The captured data is
preserved as a permanent comment block in `command.c`.

### Captured init sequence (both boards, both Linux and SDK firmwares)

The very first 7 chip commands morselib sends before anything mesh-related:

| # | Opcode | Name | vif | plen | Decoded payload |
|---|---|---|---:|---:|---|
| 1 | 0x0002 | GET_VERSION | 65535 | 0 | (query) |
| 2 | 0x0004 | ADD_INTERFACE | 65535 | 10 | initial monitor/scan VIF |
| 3 | 0x0025 | GET_CAPABILITIES | 0 | 0 | (query) |
| 4 | 0x0016 | CONFIG_PS | 0 | 2 | basic PS setup |
| 5 | 0x003e | GENERIC_PARAM(SET) | 0 | 16 | pid=2 TX_STATUS_FLUSH_WATERMARK=10 |
| 6 | 0x003e | GENERIC_PARAM(SET) | 65535 | 16 | pid=18 DYNAMIC_PS_TIMEOUT_MS=100 |
| 7 | 0x0019 | HEALTH_CHECK | 65535 | 0 | (query) |

### Critical correction to action semantics

The embedded morselib defines:
```c
enum morse_cmd_param_action {
    MORSE_CMD_PARAM_ACTION_SET = 0,
    MORSE_CMD_PARAM_ACTION_GET = 1,
    MORSE_CMD_PARAM_ACTION_LAST = 2,
};
```

This is the **opposite** of the Linux convention (which has SET=1, GET=0).
Initial decode of the captured payload had action=0 mis-interpreted as GET;
correct interpretation is SET.

Additionally, the morselib struct field order swaps `flags` and `value`
relative to the Linux struct:
- Linux: `{hdr, param_id, action, value, flags}`
- morselib: `{hdr, param_id, action, flags, value}`

After correcting both: CMDTX#5 sets parameter 2 (TX_STATUS_FLUSH_WATERMARK)
to value 10 (which exactly matches `MM_TX_STATUS_BUFFER_FLUSH_WATERMARK (10)`
in `umac_interface.c`). CMDTX#6 sets parameter 18 (DYNAMIC_PS_TIMEOUT_MS)
to value 100.

### Comparison to Linux init

Linux's `morse_mac_register()` through `ieee80211_register_hw()` sends
ZERO chip commands. The first command Linux sends is `GET_VERSION` when
mac80211 calls the start callback. Then commands fire only when interfaces
are added by user space.

morselib sends 4 boot-init commands that Linux never sends at boot:
`CONFIG_PS`, `GENERIC_PARAM(SET)` ×2, `HEALTH_CHECK`. But — and this is
the key conclusion — those 4 commands set mundane PS/TX-queue parameters
to documented sensible values. **None of them is a "mode lock" or
"strict RX filter" command.**

### Implications for mesh RX

The chip-command interface does NOT carry the asymmetry that explains why
mac80211 mesh works on the Linux firmware but our morselib-driven mesh
doesn't. The 7 commands morselib sends at boot are all benign config.

Combined with Phase 4i (firmware swap to Linux variants exhibited
identical mesh-RX-blocked behavior), this leaves **one remaining
host→chip path** for the mode lock: **direct chip-RAM writes via
`morse_trns_write_le32()` / `morse_trns_read_le32()`** that morselib
performs during boot, bypassing the command channel.

### Phase 4k (proposed next step)

Instrument `morse_trns_write_le32` and `morse_trns_read_le32` similarly to
log every direct chip-register access during boot. Look for register writes
that could correspond to "RX filter mode" hardware registers. If morselib
writes a register the Linux driver doesn't, that's the lock.

If THIS exploration also comes up empty, the conclusion is that the chip
defaults to fullmac-strict RX and the Linux driver inherits a permissive
default from some chip-internal POR state morselib's boot sequence
disturbs. At that point we'd genuinely be out of host-side avenues and
the Morse Micro support ticket is the only path.

The remaining possibilities (in order of decreasing likelihood):

1. **The 0x1005406c=0xef register write** could be a mode-config. Testing

2. **mac80211 mesh on Linux may not actually work end-to-end** on the
   public mm6108 firmware either — possible that OpenWrt's mesh claim is
   theoretical, untested in production. We can't validate without a

3. **A chip-internal default that the SDK firmware enters during boot

   eFuse value, or BCF (board config file) content. The BCF file is
   loaded at boot (we see the load_addr 0x8011fa80 in MMFW); maybe the
   BCF's first byte encodes "fullmac vs softmac".

4. **The Linux driver, when paired with mac80211, sends specific TX
   frames at init (like a "hello world" probe req) that prime the chip
   into a different RX state.** This would be unrelated to commands or
   registers — purely over-the-air timing.

## Phase 4l — RX-path reverse engineering + the fullmac-mesh-delivery theory

Goal directive: "get mesh peer mode working; reverse-engineer anything needed."

### 1. Decoded every boot-time chip-register write (hypothesis killed)

Phase 4k flagged `0x1005406c = 0x000000ef` as a suspicious "feature register."
Source-traced it definitively in `mm6108/mm6108.c`:

| Boot write addr | Register macro | Purpose |
|---|---|---|
| 0x10058094 | MM6108_REG_AON_ADDR | always-on domain |
| 0x1005807c | MM6108_REG_AON_LATCH_ADDR | AON latch |
| 0x1005406c | **MM6108_REG_CLK_CTRL** (=0xef) | **clock control, not a filter** |
| 0x02000000 | MM6108_REG_MSI | MSI interrupt trigger |
| 0x10054d40 | MM6108_REG_MANIFEST_PTR_ADDRESS | chip-ready poll target |
| 0x10054050 | MM6108_REG_RESET (=0xDEAD) | CPU reset |
| 0x100a60xx | MM6108_REG_INT_BASE region | interrupt config |
| 0x100acxxx | pager/trigger registers | page DMA setup |

`0x1005406c=0xef` is the **clock-control register** init value (paired with
`MM6108_REG_EARLY_CLK_CTRL_VALUE=0xe5`). Linux writes the identical value
via `MORSE_REG_CLK_CTRL`. **No boot register write is an RX-mode or filter
control.** The "secret mode register" hypothesis is conclusively dead.

### 2. Host-side RX filter cleared

`umac_datapath_set_filter_all_beacons()` exists and STA mode toggles it, but:
- `filter_beacons` defaults to **false** (zero-init struct field), so the
  host beacon filter would NOT drop mesh beacons.
- More importantly it runs *below* `mmdrv_host_process_rx_frame` (the chip
  shim), which never fires in mesh mode — so nothing reaches this filter.

The host RX path is not the blocker. The wall is purely chip→host delivery.

### 3. No monitor / promiscuous RX command exists

Searched the entire chip command set for monitor/sniffer/promiscuous/raw-RX
opcodes. The only `monitor_bssid` field belongs to `morse_cmd_standby_enter`
(wake-on-WLAN), unrelated to RX delivery. **There is no chip command to force
raw-frame delivery to the host.**

### 4. The fullmac-mesh-delivery theory (current best explanation)

Synthesizing Phases 4f–4l:

- Phase 4g proved Linux's **fullmac path (`wiphy.c`) has ZERO mesh code** —
  mesh on the MM6108 is implemented **only** in the softmac (mac80211) path,
  where the chip delivers raw 802.11 frames and the host stack does mesh.
- Phase 4f proved the chip **accepts every mesh command and TXes beacons**
  (mesh_tbtt task runs) but delivers **zero RX frames and zero events** to
  the host.
- Phase 4i: swapping in Linux softmac/thin-LMAC firmware didn't help — but
  that's an impedance mismatch: morselib is a *fullmac* driver; softmac
  firmware expects a softmac (mac80211-style) host driver to pull raw frames.
- Phases 4j/4k: no host command or register configures an RX mode that
  changes this.

**Theory: the SDK fullmac MM6108 firmware can TRANSMIT mesh beacons but has
no path to DELIVER received mesh peer frames/events to the host, because the
fullmac architecture has no host-side mesh consumer. Mesh RX→host is a
softmac-only capability on this silicon.**

If true, mesh peer mode is **impossible** with `fullmac firmware + morselib`
regardless of host configuration. The paths to working mesh would be:
1. A softmac/mac80211 host-stack port (Phase 4g: ~100k LOC, multi-month), or
2. A Morse-provided fullmac firmware build that delivers mesh RX events, or
3. Pivot to STA+AP peer-to-peer (works on fullmac today).

### 5. The keystone test — BUILT, awaiting hardware

Added a **bus-level RX channel histogram** at `morse_skbq_process_rx`
(skbq.c) that logs every page the chip pushes to the host, by channel:
- COMMAND (0xFE) + TX_STATUS (0xFF) only  →  chip delivers ZERO RX frames
  in mesh mode (theory CONFIRMED → mesh needs the softmac port).
- DATA (0x00) / BEACON (0x03) / MGMT (0x04) pages appear  →  chip IS
  delivering frames; the drop is host-side and FIXABLE (theory refuted,
  new avenue opens).

Both mesh boards already beacon (chip TX confirmed working), so flashing
this build on both boards and reading the histogram is a single decisive
test. The build compiles clean (`warthog-mesh-smoke`).

**Status: blocked on hardware.** The Plugable USB hub and both XIAO boards
are currently disconnected (no `/dev/cu.usbmodem*`, `uhubctl` reports no
compatible devices). The instant hardware is reconnected, flashing the
current `warthog-mesh-smoke` build and capturing the `RXCHAN` log lines
resolves the theory either way.

## Phase 4l (cont.) — PRIMARY-SOURCE CONFIRMATION: mesh is not supported on the ESP32 SDK

The "fullmac firmware has no mesh-RX→host path" theory is now confirmed by
Morse Micro's own authoritative sources, not just our reverse engineering:

### 1. Official ESP32 SDK repo (github.com/MorseMicro/mm-iot-esp32)

Documents **STA (station) mode only**. The only WLAN examples are
`sta_connect` and `scan`. There is **no mention of AP mode or 802.11s
mesh / mesh point mode anywhere**. The repo is explicitly described as an
"alpha port" that "may be incomplete in the set of supported features."

### 2. Morse Micro community forum

- "AP support for MM6108 on ESP32 SDK" (Apr 2025): only STA mode available.
- As of January 2026: AP mode for ESP32 was *expected by end of 2025 but
  not yet released*.
- 802.11s mesh on the MM6108 is described only in the context of the
  **Linux eval kit** ("Mesh Gate" = mesh + AP), never the ESP32 SDK.

### Conclusion

**Mesh peer mode is not achievable on the current XIAO ESP32-S3 + Seeed
HaLow (MM6108) + MM-IoT-ESP32 SDK.** The platform supports STA mode only.
Even AP mode — a prerequisite simpler than mesh — was unreleased as of
early 2026.

This explains every empirical observation across Phases 4f–4l with zero
remaining anomalies:

| Observation | Explanation |
|---|---|
| Chip accepts MESH_CONFIG, BSS_BEACON_CONFIG, etc. | Commands exist in the shared chip ABI (used by Linux), so the chip parses them |
| Chip TXes mesh beacons (TX_STATUS fires) | Basic beacon TX path works |
| Chip delivers ZERO RX frames + ZERO events in mesh mode | The ESP32 fullmac firmware/SDK has no mesh-peer→host path — mesh isn't wired up on this port |
| No host command/register opens mesh RX | There is none to find; the feature isn't implemented in this SDK |
| Swapping Linux firmware variants didn't help | morselib (fullmac driver) can't drive softmac firmware, and the fullmac path has no mesh |

### Realistic paths to working mesh (all external or multi-month)

1. **Wait for Morse Micro to release mesh (or at least AP) support on the
   MM-IoT-ESP32 SDK.** AP was already targeted; mesh would follow. This is
   the lowest-effort path but depends on Morse's roadmap.
2. **Port the Linux softmac/mac80211 mesh stack** to drive the chip with
   softmac firmware (Phase 4g: ~100k LOC, multi-engineer-year — infeasible
   in this project's scope; scaffold exists at `components/halow_mesh_compat/`).
3. **Pivot to STA + Mesh-Gate-AP** once Morse ships ESP32 AP mode — gives
   multi-node connectivity without true 802.11s peering.

The host-side investigation is **complete and conclusive**. Every byte
crossing the host↔chip interface has been audited; every host-controllable
