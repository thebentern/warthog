## What was fixed

| Bug | Symptom | Fix |
|---|---|---|
| H1 | `AT+MESHBRIDGE=1` never formed a bridge and took networking down | `main/mesh_bridge.c` rewritten, whole-or-nothing; USB link held down until the bridge decision is made |
| H2 | Batman mode ran out of heap | PSRAM heap (`main/ext_ram.c`), NAPT allocated at boot behind a heap gate, Wi-Fi moved out of IRAM; `AT+HEAP?` and `AT+EXTRAM` added |
| H3 | `AT+MESHSEC=` on an SAE build dropped every link until reboot | Store-only on SAE builds; the web flasher asks `AT+MPMPEERS?` first and fails closed |
| H4 | `AT+MPING` freed its semaphore while the ping task still ran | Synchronous ping on a raw ICMP socket in the AT task |
| H5 | An open mesh peered with any node whatever its mesh ID | Mesh profile check on peering (Part A of the design only) |
| H6 | USB died when the console was opened and closed under network load | Vendored esp_tinyusb with two changes (below) |

Also fixed along the way: batman now refuses to start without the PSRAM heap (`reason=no-psram`).

## H6 needs the most care

H6 was two separate faults in TinyUSB 0.21's DWC2 driver. Both are **avoided, not root-caused**.

1. **DMA mode: the whole USB function stops** and only a power cycle recovers it. Avoided by building the driver in slave mode: `CFG_TUD_DWC2_DMA_ENABLE 0` in `components/esp_tinyusb/include/tusb_config.h`.
2. **Slave mode: the console alone goes silent**, network still up, when a reply longer than one 64-byte packet is in flight while the host sends control requests the board refuses. Avoided by four lines in `components/esp_tinyusb/tinyusb/src/tusb.c` (`tu_edpt_stream_write_xfer`, marked `Warthog H6`) that cap a FIFO-backed transfer at one packet.

Things to know before touching it:

- **The ordinary repro cannot validate a fix.** It fails only about one run in 10 to 25. A lock in `dcd_dwc2.c` passed 21 runs and then failed; it was removed. Use the fast stress (a core-1 task writing 90-byte lines every tick, plus about 2,000 refused control requests a second from the host), which fails in under a minute without the cap and ran 500 s clean with it. `tools/bench/README.md` describes all three H6 tests and `tools/bench/h6/` holds the tools.
- **Ruled out as the cause**, each by building it and watching it fail: a lock around the interrupt handler's FIFO refill, the transmit FIFO flush in the stall path, a global IN NAK around that flush, the FIFO-empty interrupt level, and either endpoint 0 stall write alone.
- **Enforcement:** glue guard 87 checks the define, the four marked lines, and that every other vendored file matches the registry's `CHECKSUMS.json`. `scripts/ci/check-image.sh` checks the ELF holds the slave mode driver. Nothing on the console tells a fixed image from an unfixed one.
- **Upgrading esp_tinyusb:** the procedure is in [fork-inventory.md](fork-inventory.md).

## Open items

- **The H6 test tooling is in the repo but its repo copies have not touched a board.** `tools/bench/h6/` has the load and stress scripts, the two libusb host tools and a register-stream listener, and `main/usbdiag.c` is the bench firmware module (compiled to nothing unless the build defines `WARTHOG_USBDIAG`). They were rewritten from the session's scratch scripts to stand alone. The normal images and the bench image build, the host tools compile and the scripts parse, but the whole bench (hub, boards, both Pi Ethernet adapters) had dropped off the Mac's USB by the time they were ready, so none of them has been run on hardware. Run test 3 in `tools/bench/README.md` once to confirm them.
- **The final 12-run soak has no baseline.** It ran with extra refused control requests alongside and passed, but was never run against an unfixed image with that traffic. The fast stress is the test with a measured before and after.
- **H5 is half done by design.** An open node still sends peering Opens toward an SAE node sharing its mesh ID, and the no-peers diagnosis can still blame the channel for a mesh-ID mismatch.
- **Medium findings M1 to M5 and the lows are not fixed.** M1 (`warthog-mesh-sae` carries no data with more than one peer) is the most serious.
- **Two low review findings were left:** a check-then-allocate race in the NAPT heap gate, and guard 87 counting stray `.DS_Store` files in the vendored tree.
- **Heap headroom under overload is 23 KB.** The report lists the levers if a fourth peer or a busy Wi-Fi client makes that too tight.
- **Not tested on this bench:** the station uplink, 2.4 GHz Wi-Fi AP clients, DNS and internet NAT, a phone or a Linux or Windows host, a fourth peer, and a board whose PSRAM does not answer.

- **Flashing:** one esptool session per `AT+DLMODE`.
- **The bench was not on the Mac's USB at the end of the session** (no hub, boards or Pi adapters visible). It was unplugged on purpose, not a fault. The board list above is as last seen.
- **The Mac's Wi-Fi is its internet uplink.** Do not join the Warthog AP from it.
