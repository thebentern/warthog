# Fork Inventory

What's local, what's upstream, and what each piece exists to work around. Everything we ship in-tree — nothing is silently vendored or patched in a way that's hard to audit later.

## `components/halow/` — local fork of `morsemicro/halow` 2.10.4-esp32-1

**Source:** [https://github.com/MorseMicro/esp-halow](https://github.com/MorseMicro/esp-halow), tag `2.10.4-esp32-1`.

**Why forked:** the registry version doesn't expose the chip's 802.11s mesh mode — it ships only STA + AP shims. We need umac mesh (`umac_mesh.h`/`umac_mesh.c`-style additions) for the multi-board topologies. See `docs/history/mesh-port-scope.md` for the scope analysis and `docs/history/mesh-port-audit.md` for the umac API audit that informed it.

**What's changed relative to upstream:**

- Non-ESP32 BSPs stripped (the registry tarball ships a kitchen sink of Nordic / NXP / STM32 ports we don't need; dropping them shaves the build and keeps the diff focused on ESP32).
- Vendor docs stripped (not load-bearing).
- Mesh additions under `components/halow/components/morselib/` — see `docs/mesh-port-*.md`.
- For batman mode (`main/bat_port.c`): `mmwlan_mesh_query_peer_links()` in `include/mmwlan_mesh.h` / `umac/mesh/mmwlan_mesh.c` and `umac_mesh.c` (a peer and rate-control snapshot taken on the umac event loop, via a new `mesh_peer_links` event in `umac/core/umac_core.h`; it returns a status, so a failed query is not an empty peer table; `mmwlan_mesh_get_peer_links()` is the count-only form), `umac_datapath_mesh_peer_links()` in `umac_datapath_mesh.c`, `umac_rc_get_expected_tput_kbps()` in `umac/rc/umac_rc.c` (theoretical throughput of rate control's best rate), and the `g_warthog_mesh_batman` gate in `umac_datapath.c`: with `AT+MESHGRP=0` (default) group frames take the Address Extension mode 2 replica shape, with `1` they stay standard group frames, and leaf proxy learning is off. In the same file a unicast whose RA names a peer AMPE has not keyed yet returns `MMWLAN_NOT_FOUND` instead of being queued and dropped.
- Mesh peer records across tasks (`umac_datapath_mesh.c`, `umac_datapath.c`). Peers are added and deleted on the umac event loop, but `umac_datapath_tx_frame()` (lwIP's tcpip thread, the batman engine task) and the receive filter in `umac_datapath_rx_frame()` (the chip driver task) look them up on their own tasks; in mesh mode both run between `umac_datapath_mesh_read_begin()` and `umac_datapath_mesh_read_end()`. `umac_datapath_mesh_del_peer()` unlinks a peer and takes its queue in one critical section, releases the frames after it, and frees the record only once every reader inside at that moment has left; until then its slot is not reused. Readers alternate between two counts, so later readers cannot hold a record back, and neither side ever waits for the other. `mesh_queue_one_()` queues only to a peer still in the table.
- Receive replay counters per TID for QoS data (`umac/keys/umac_keys.h`, `umac_datapath.c`; the key RSC seeds every TID's counter in `supplicant_shim/driver.c` and `driver_ap.c`), as 802.11 requires and mac80211 does: a peer's frames on two access categories can arrive with their PNs interleaved.
- Receive filter, unicast data not addressed to us (`umac_datapath_rx_frame_filter()` in `umac_datapath.c`). In mesh mode the MM6108 hands up unicast data frames addressed to other stations (measured on air on 2026-09-30: another Warthog's frames to an OpenMANET node, which host CCMP then tried under the sender's pairwise key and counted as `micfail`). A mesh data frame whose receiver address (addr1) is unicast and not ours is now dropped after the unknown-sender and own-source checks and before the duplicate check, so it reaches neither the sender's duplicate state, its Block Ack reorder window, host CCMP nor the chip-decrypted path; counted as filter reason 9 (`g_warthog_filt_hist[9]`, now ten entries, in `main/at.c`; `not_ours` in `AT+FILTSTAT?`). An 802.11s unicast relayed through us carries our address in addr1, so relaying is unchanged; group-addressed frames and management frames are not judged. Ahead of the pre-association gate, a mesh unicast management frame other than a beacon whose addr1 is not our mesh address (`umac_mesh_own_addr()`, now declared in `umac/mesh/umac_mesh.h`) is counted and its first 16 octets kept, not dropped (`g_warthog_filt_mgmt_nours` and `g_warthog_filt_mgmt_nours_hdr` in `main/at.c`; `mgmt_nours` on the second line of `AT+FILTSTAT?`): whether the chip hands those up is not measured, and until it is they still reach host CCMP, Block Ack and path selection. STA and AP modes are unchanged: the firmware never enables them (`main/` calls neither `mmwlan_sta_enable()` nor `mmwlan_ap_enable()`), and there upstream relies on the chip's own receiver-address filter.
- Block Ack and peer teardown (`umac/ba/umac_ba.c`, `umac_datapath.c`). `umac_ba_deinit()` cancels each TID's pending ADDBA request retry before it clears the sessions; mesh `del_peer` needs this, since the retry otherwise fires on a freed peer record. It also runs on STA disconnect (`umac/connection/umac_connection.c`), so client mode now cancels its retries there too; that path is not host-tested. `umac_datapath_stad_teardown()` (new in `umac_datapath.c`, called with `umac_ba_deinit()` from `umac_datapath_mesh_del_peer()`) cancels the RX reorder timeout and releases the reorder list and defrag state. `umac_datapath_tx_mgmt_frame()` has a mesh branch in place of the STA PMF logic: a robust unicast management frame (Block Ack) to a peer that runs MFP is protected as its path selection is, by `umac_datapath_mesh_protect_mgmt()` in `umac_datapath_mesh.c` — marked for the chip's CCMP, or sealed with host CCMP while it is on (`-swccmp` builds); a frame that cannot be sealed is dropped and counted (`tx_fail` in `AT+SWCCMP?`), never sent in the clear. Each one is also counted in `AT+MESHFWDSTAT?` (`mgmt tx chip`/`host`/`drop`, `g_warthog_mgmt_tx_*` defined in `main/at.c`).
- Group path selection under SAE is group-addressed privacy, as mac80211 does it (`net/mac80211/rx.c` `ieee80211_rx_h_decrypt`, `tx.c` `ieee80211_select_link_key`; 802.11 Table 9-47). In `umac/mesh/umac_mesh.c` our own group PREQs and PERRs go out Protected under our own MGTK, sealed by the chip (`HW_ENC` under its key id, no MMIE; `UMAC_MESH_HWMP_PROT_GROUP` from `umac_datapath_mesh_hwmp_tx_key()`) and counted in flight under that MGTK until their TX status, as our group data is (`mesh.own_group`); before hostap delivers our MGTK, or while its chip install has failed, they go in the clear. In `umac_datapath.c` `umac_datapath_process_mgmt_frame_ccmp_header()` refuses, before any replay counter moves, a Protected group management frame the chip opened (its only group key is our own MGTK, which every peer holds) and one host CCMP opened under a key id that is not the sender's MGTK, then replay-checks the rest on that MGTK's management counter; `umac_datapath_mesh_hwmp_rx_ok()` in `umac_datapath_mesh.c` takes a Protected group frame from any keyed peer and refuses every one in the clear, with a BIP MMIE of either length (`umac_mesh_bip_has_mmie()`) or without, whatever the peer's MFP: stricter than mac80211, so a relay never re-sends under our MGTK what anyone could have sent in a peer's name; `umac_mesh_fwd_glue_hwmp_rx()` refuses one in the clear too. Only host CCMP (`-swccmp` builds) can open a peer's, so on the chip-crypto images Warthogs no longer take each other's. Counted in `AT+MESHFWDSTAT?` (`hwmp gp`, `hwmp tx gp`/`plain`, `mgmt gp nodec`/`own`/`key`/`replay`). Written from mac80211's source and host-tested after an on-air failure against OpenMANET 1.8.0 on 2026-09-29, where every group PREQ was refused; on air on 2026-09-30 the nodes' group PREQs were taken and they held an `ACTIVE` path to the Warthog. Not measured: whether the chip seals our group path selection and, on the swccmp builds (`WARTHOG_MESH_MGTK_PN_BASE`), starts our MGTK at the TX PN `INSTALL_KEY` gives it, which the Key RSC AMPE advertises assumes.
- Mesh chip interface type (`umac/interface/umac_interface.c`, `umac_mesh.c`, `umac_datapath_mesh.c`, `umac/ps/umac_ps.c`, `driver/driver.c`, `driver/beacon/beacon.c`). The board boots the chip with a STA-type interface and, by default, the mesh runs on it; with `WARTHOG_MESH_CHIP_VIF_MESH=1` (`warthog-mesh-sae-swccmp-meshvif`) `umac_interface_add(MESH)` replaces it with `ADD_INTERFACE` type 5 and that interface's `GET_CAPABILITIES`, as Linux adds a mesh point, and falls back to a STA interface when the chip refuses it, gives it an id other than 0 (beacons and data are tagged VIF 0), or `REMOVE_INTERFACE` fails. On a MESH interface there is no `BSSID_SET` (mac80211 sends none at mesh start) and no `BSS_BEACON_CONFIG` (Linux sends it only when beaconing restarts), a leaving peer goes 3, 2, 1 with no survivor re-registration (their keys still go back), no `CONFIG_PS` goes to it, and a host beacon tick yields to a chip that schedules its own beacons (`morse_beacon_host_tick_yields()` in `beacon.h`). A MESH interface starts beaconless: `MESH_CONFIG(START)` with `enable_beaconing` 0 and MBCA and its timers 0, as the OpenMANET Pis send it; the host timer still sends every beacon. A STA interface keeps the fork's beaconing tuple (`enable_beaconing` 1, MBCA and its timers 0), one Linux never sends; on a MESH interface it hung the board about 2 s after the firmware started, USB gone, no reboot and no coredump (on air, 2026-09-30). `mmdrv_add_if_status()`, `mmdrv_get_capabilities_status()`, `mmdrv_update_sta_state_status()`, `mmdrv_install_key_status()` and a status out on `mmdrv_set_bssid()` / `mmdrv_cfg_bss_beacon()` / `mmdrv_mesh_config()` return the chip's own status, which `morse_cmd_tx()` drops when given a response buffer; refusals are counted on every build. On every build `mmdrv_install_key()` now returns a key the chip refused as an error, where it took it as installed or asserted on the index the reply never carried; a MESH-interface build counts an accepted key at another hardware index instead of asserting. The start's `RESULT:` line (`main/mesh.c`, `warthog_mesh_start_result()` in `main/mesh_diag.c`) says what the chip answered. Shown in `AT+MESHCFG?` (`chip_vif=`, `chip_refused`) and `AT+BCNSTAT?` (`chip_irq`, `host_yield`); host-tested by `test_simnode_meshvif{,_off}`, which link the real `umac_interface.c` (`simnode/interface_seam.c`), the existing simnode suites rebuilt with the flag (`*_meshvif`), and `test_chipvif_glue{,_off}`, which run `driver.c`'s status reads and `MESH_CONFIG` bytes, `beacon.c` and `umac_ps.c`. On air on 2026-09-30 (`-meshvif`, two OpenMANET 1.8.0 Pis at RTS threshold 1000 and a second Warthog): `chip_vif=mesh(5) vif_id=0 fallback=0`; the chip accepted `MESH_CONFIG` and the BSS configuration, where on a STA interface it refuses `MESH_CONFIG` and `BSS_BEACON_CONFIG` with status -17 and the mesh runs regardless; SAE peering with all three, host CCMP, Warthog to Warthog pings both ways; a Pi's 1000-byte frames now get a CTS whichever peer registered last, where on a STA interface only that peer's did (`wiki/OpenMANET-Interop.md`, *Frames over about 1000 bytes from a Linux node*); batman mode; beacons host-sent (`chip_irq` 0). Not measured on a MESH interface: the SAE builds with chip keys, an open mesh, three or more Warthogs, recovery after a chip restart (a restart under an active mesh asserts, so the board reboots), and a soak longer than the 54-minute one on 2026-09-30 (237/240 1000-byte pings from the Pis, 60/60 Warthog to Warthog, no fallback).
- Re-check the seven entries above against any morselib upgrade; their declarations are in `umac_datapath.h`, `umac_datapath_private.h`, `umac/rc/umac_rc.h`, `umac/interface/umac_interface.h` and `internal/mmdrv.h`. `make -C components/halow_mesh_compat/test all` links the real `umac_ba.c`, `umac_datapath.c`, `umac_datapath_mesh.c`, `umac_mesh.c` and `umac_interface.c` and fails if the ADDBA cancel, the teardown, the Block Ack protection, group path selection's group-addressed privacy, the receive filter's not-ours drop or the mesh chip interface type is lost.

**How it's wired:** `main/idf_component.yml` has:

```yaml
morsemicro/halow:
  version: "2.10.4-esp32-1"
  override_path: "../components/halow"
```

The directory is named `halow` (the dependency short name) so the IDF component graph resolves `main`'s `REQUIRES halow` to this fork rather than to a registry pull.

**Upgrade path:** when Morse Micro tags `2.11.x-esp32-N`, re-vendor the new tarball, strip non-ESP32 BSPs + docs again, replay the mesh additions, and bump the `version:` line. The build script (`pre_build_morselib.py`) patches one CMakeLists line at build time; that patch will need to be re-verified against any morselib reorg upstream.

## `components/firmware/` — thin local IDF component shim (not a fork)

**Why it exists:** `morsemicro/halow`'s shims link against `idf::firmware`, but the registry publishes the binary blobs as `morsemicro/firmware` (note the namespace prefix). IDF's component graph won't resolve `idf::firmware` to a prefixed package automatically, so this 60-line shim component sits in between:

- Pulls the `.mbin` blobs from `managed_components/morsemicro__firmware/` (which the registry populates).
- Exposes them under the bare `firmware` component name so `idf::firmware` resolves.
- Picks the right BCF + firmware file based on `CONFIG_MM_BCF_FILE` / `CONFIG_MM_FW_FILE` / `CONFIG_MMHAL_CHIP_TYPE_*` (Kconfig is a direct copy of upstream's).

**Upstream changes that obsolete this:** if Morse Micro renames the registry package to drop the namespace prefix, or if their shim starts using `idf::morsemicro__firmware` directly, this shim can be deleted.

## `scripts/pre_build_morselib.py` — PlatformIO build hook

**Why it exists:** PlatformIO + ESP-IDF + the `morselib` CMake custom command don't compose cleanly out of the box. Three concrete bugs this hook works around:

1. **PlatformIO's section scanner runs `objdump -h` on every `.a` before CMake's custom commands fire** — so `libmorse.a` doesn't exist yet when scanned, the build aborts. The hook pre-runs `ar -M` + `ranlib` + `librarymangler.py` (the upstream Morse symbol-mangler) so the mangled archive exists before PIO scans.
2. **The `components/firmware/` CMake custom-command for objcopying `.mbin → .o` doesn't fire under PIO**, so the hook does the objcopy itself (same flags, same output object names).
3. **morselib's `IMPORTED` target lacks a dep on the custom command that produces its file** — we patch one line into `components/halow/components/morselib/CMakeLists.txt` (in-tree, with a `# warthog:` marker so it's idempotent) to wrap `libmorse.a` in `-Wl,--whole-archive`. A direct `add_dependencies()` would form a cycle.

The hook is wired in `platformio.ini`:

```ini
extra_scripts = pre:scripts/pre_build_morselib.py
```

**Upstream changes that obsolete this:** if PlatformIO's section scanner learns to run after CMake custom commands, or if Morse Micro restructures their CMake to not need the mangler step, this script can shrink or disappear. The `.mbin → .o` objcopy will likely always be needed under PIO until PIO + IDF custom-command timing is fixed.

## What we don't fork

- `morsemicro/firmware` — pulled from the registry as-is into `managed_components/`. No patches.
- `espressif/esp_tinyusb` — registry, no patches.
- `espressif/tinyusb` — registry, no patches.
- ESP-IDF — pinned via the `pioarduino/platform-espressif32` fork (which itself just upgrades the IDF version from PIO's bundled 5.1.4 to 5.5.4 — no code changes).

## Audit checklist for the next morsemicro/halow upgrade

1. Pull the new tarball into a scratch dir.
2. `diff -r` against `components/halow/` to identify upstream changes vs. our deletions.
3. Re-apply: strip non-ESP32 BSPs, strip docs, re-vendor mesh additions.
4. Verify the morselib `CMakeLists.txt` line that `pre_build_morselib.py` patches still exists at the expected location (search for `set_target_properties(morselib PROPERTIES IMPORTED_LOCATION`).
5. Bump `version:` in `main/idf_component.yml`.
6. Smoke build: `pio run -e warthog-us`.
7. Host suite: `make -C components/halow_mesh_compat/test clean all`, then `make -C components/halow_mesh_compat/test clean all SAN=1` (without `clean` the sanitizer run reuses the plain binaries).
8. Bench test through the full bench-test checklist in the README.
