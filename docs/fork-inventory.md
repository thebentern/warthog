# Fork Inventory

What's local, what's upstream, and what each piece exists to work around. Everything we ship in-tree — nothing is silently vendored or patched in a way that's hard to audit later.

## `components/halow/` — local fork of `morsemicro/halow` 2.10.4-esp32-1

**Source:** [https://github.com/MorseMicro/esp-halow](https://github.com/MorseMicro/esp-halow), tag `2.10.4-esp32-1`.

**Why forked:** the registry version doesn't expose the chip's 802.11s mesh mode — it ships only STA + AP shims. We need umac mesh (`umac_mesh.h`/`umac_mesh.c`-style additions) for the multi-board topologies. See `docs/history/mesh-port-scope.md` for the scope analysis and `docs/history/mesh-port-audit.md` for the umac API audit that informed it.

**What's changed relative to upstream:**

- Non-ESP32 BSPs stripped (the registry tarball ships a kitchen sink of Nordic / NXP / STM32 ports we don't need; dropping them shaves the build and keeps the diff focused on ESP32).
- Vendor docs stripped (not load-bearing).
- Mesh additions under `components/halow/components/morselib/` — see `docs/mesh-port-*.md`.
- For batman mode (`main/bat_port.c`): `mmwlan_mesh_query_peer_links()` in `include/mmwlan_mesh.h` / `umac/mesh/mmwlan_mesh.c` and `umac_mesh.c` (a peer and rate-control snapshot taken on the umac event loop, via a new `mesh_peer_links` event in `umac/core/umac_core.h`; it returns a status, so a failed query is not an empty peer table; `mmwlan_mesh_get_peer_links()` is the count-only form), `umac_datapath_mesh_peer_links()` in `umac_datapath_mesh.c`, `umac_rc_get_expected_tput_kbps()` in `umac/rc/umac_rc.c` (theoretical throughput of rate control's best rate), and the `g_warthog_mesh_batman` gate in `umac_datapath.c`: with `AT+MESHGRP=0` (default) group frames take the Address Extension mode 2 replica shape, with `1` they stay standard group frames, and leaf proxy learning is off. In the same file a unicast whose RA names a peer AMPE has not keyed yet returns `MMWLAN_NOT_FOUND` instead of being queued and dropped.
- Mesh peer records across tasks (`umac_datapath_mesh.c`, `umac_datapath.c`). Peers are added and deleted on the umac event loop, but `umac_datapath_tx_frame()` (lwIP's tcpip thread, the batman engine task) and the receive filter in `umac_datapath_rx_frame()` (the chip driver task) look them up on their own tasks; in mesh mode both run between `umac_datapath_mesh_read_begin()` and `umac_datapath_mesh_read_end()`. `umac_datapath_mesh_del_peer()` unlinks a peer and takes its queue in one critical section, releases the frames after it, and frees the record only once every reader inside at that moment has left; until then its slot is not reused. Readers alternate between two counts, so later readers cannot hold a record back, and neither side ever waits for the other. `mesh_queue_one_()` queues only to a peer still in the table.
- Receive replay counters per TID for QoS data (`umac/keys/umac_keys.h`, `umac_datapath.c`; the key RSC seeds every TID's counter in `supplicant_shim/driver.c` and `driver_ap.c`), as 802.11 requires and mac80211 does: a peer's frames on two access categories can arrive with their PNs interleaved.
- Receive filter, unicast data not addressed to us (`umac_datapath_rx_frame_filter()` in `umac_datapath.c`). In mesh mode the MM6108 hands up unicast data frames addressed to other stations (measured on air on 2026-09-30: another Warthog's frames to an OpenMANET node, which host CCMP then tried under the sender's pairwise key and counted as `micfail`). A mesh data frame whose receiver address (addr1) is unicast and not ours is now dropped after the unknown-sender and own-source checks and before the duplicate check, so it reaches neither the sender's duplicate state, its Block Ack reorder window, host CCMP nor the chip-decrypted path; counted as filter reason 9 (`g_warthog_filt_hist[9]`, now ten entries, in `main/at.c`; `not_ours` in `AT+FILTSTAT?`). An 802.11s unicast relayed through us carries our address in addr1, so relaying is unchanged; group-addressed frames and management frames are not judged. Ahead of the pre-association gate, a mesh unicast management frame other than a beacon whose addr1 is not our mesh address (`umac_mesh_own_addr()`, now declared in `umac/mesh/umac_mesh.h`) is counted and its first 16 octets kept, not dropped (`g_warthog_filt_mgmt_nours` and `g_warthog_filt_mgmt_nours_hdr` in `main/at.c`; `mgmt_nours` on the second line of `AT+FILTSTAT?`): whether the chip hands those up is not measured, and until it is they still reach host CCMP, Block Ack and path selection. STA and AP modes are unchanged: the firmware never enables them (`main/` calls neither `mmwlan_sta_enable()` nor `mmwlan_ap_enable()`), and there upstream relies on the chip's own receiver-address filter.
- Block Ack and peer teardown (`umac/ba/umac_ba.c`, `umac_datapath.c`). `umac_ba_deinit()` cancels each TID's pending ADDBA request retry before it clears the sessions; mesh `del_peer` needs this, since the retry otherwise fires on a freed peer record. It also runs on STA disconnect (`umac/connection/umac_connection.c`), so client mode now cancels its retries there too; that path is not host-tested. `umac_datapath_stad_teardown()` (new in `umac_datapath.c`, called with `umac_ba_deinit()` from `umac_datapath_mesh_del_peer()`) cancels the RX reorder timeout and releases the reorder list and defrag state. `umac_datapath_tx_mgmt_frame()` has a mesh branch in place of the STA PMF logic: a robust unicast management frame (Block Ack) to a peer that runs MFP is protected as its path selection is, by `umac_datapath_mesh_protect_mgmt()` in `umac_datapath_mesh.c` — marked for the chip's CCMP, or sealed with host CCMP while it is on (`-swccmp` builds); a frame that cannot be sealed is dropped and counted (`tx_fail` in `AT+SWCCMP?`), never sent in the clear. Each one is also counted in `AT+MESHFWDSTAT?` (`mgmt tx chip`/`host`/`drop`, `g_warthog_mgmt_tx_*` defined in `main/at.c`).
- Group path selection under SAE is group-addressed privacy, as mac80211 does it (`net/mac80211/rx.c` `ieee80211_rx_h_decrypt`, `tx.c` `ieee80211_select_link_key`; 802.11 Table 9-47). In `umac/mesh/umac_mesh.c` our own group PREQs and PERRs go out Protected under our own MGTK, sealed by the chip (`HW_ENC` under its key id, no MMIE; `UMAC_MESH_HWMP_PROT_GROUP` from `umac_datapath_mesh_hwmp_tx_key()`) and counted in flight under that MGTK until their TX status, as our group data is (`mesh.own_group`); before hostap delivers our MGTK, or while its chip install has failed, they go in the clear. In `umac_datapath.c` `umac_datapath_process_mgmt_frame_ccmp_header()` refuses, before any replay counter moves, a Protected group management frame the chip opened under anything but the sender's MGTK at its AID (on every build but `warthog-mesh-sae-meshvif` its only group key is our own MGTK, which every peer holds) and one host CCMP opened under a key id that is not the sender's MGTK, then replay-checks the rest on that MGTK's management counter; `umac_datapath_mesh_hwmp_rx_ok()` in `umac_datapath_mesh.c` takes a Protected group frame from any keyed peer and refuses every one in the clear, with a BIP MMIE of either length (`umac_mesh_bip_has_mmie()`) or without, whatever the peer's MFP: stricter than mac80211, so a relay never re-sends under our MGTK what anyone could have sent in a peer's name; `umac_mesh_fwd_glue_hwmp_rx()` refuses one in the clear too. Only host CCMP (`-swccmp` builds), or on `warthog-mesh-sae-meshvif` the chip holding the peer's MGTK at its AID (below), can open a peer's, so on the other chip-crypto images Warthogs no longer take each other's. Counted in `AT+MESHFWDSTAT?` (`hwmp gp`, `hwmp tx gp`/`plain`, `mgmt gp nodec`/`own`/`key`/`replay`). Written from mac80211's source and host-tested after an on-air failure against OpenMANET 1.8.0 on 2026-09-29, where every group PREQ was refused; on air on 2026-09-30 the nodes' group PREQs were taken and they held an `ACTIVE` path to the Warthog. Not measured: whether the chip seals our group path selection and, on the swccmp builds (`WARTHOG_MESH_MGTK_PN_BASE`), starts our MGTK at the TX PN `INSTALL_KEY` gives it, which the Key RSC AMPE advertises assumes.
- Mesh chip interface type (`umac/interface/umac_interface.c`, `umac_mesh.c`, `umac_datapath_mesh.c`, `umac/ps/umac_ps.c`, `driver/driver.c`, `driver/beacon/beacon.c`). The board boots the chip with a STA-type interface and, by default, the mesh runs on it; with `WARTHOG_MESH_CHIP_VIF_MESH=1` (`warthog-mesh-sae-swccmp-meshvif`, and `warthog-mesh-sae-meshvif` with AMPE keys in the chip) `umac_interface_add(MESH)` replaces it with `ADD_INTERFACE` type 5 and that interface's `GET_CAPABILITIES`, as Linux adds a mesh point, and falls back to a STA interface when the chip refuses it, gives it an id other than 0 (beacons and data are tagged VIF 0), or `REMOVE_INTERFACE` fails. On a MESH interface there is no `BSSID_SET` (mac80211 sends none at mesh start) and no `BSS_BEACON_CONFIG` (Linux sends it only when beaconing restarts), a leaving peer goes 3, 2, 1 with no survivor re-registration (their keys still go back), no `CONFIG_PS` goes to it, and a host beacon tick yields to a chip that schedules its own beacons (`morse_beacon_host_tick_yields()` in `beacon.h`). A MESH interface starts beaconless: `MESH_CONFIG(START)` with `enable_beaconing` 0 and MBCA and its timers 0, as the OpenMANET Pis send it; the host timer still sends every beacon. A STA interface keeps the fork's beaconing tuple (`enable_beaconing` 1, MBCA and its timers 0), one Linux never sends; on a MESH interface it hung the board about 2 s after the firmware started, USB gone, no reboot and no coredump (on air, 2026-09-30). `mmdrv_add_if_status()`, `mmdrv_get_capabilities_status()`, `mmdrv_update_sta_state_status()`, `mmdrv_install_key_status()` and a status out on `mmdrv_set_bssid()` / `mmdrv_cfg_bss_beacon()` / `mmdrv_mesh_config()` return the chip's own status, which `morse_cmd_tx()` drops when given a response buffer; refusals are counted on every build. On every build `mmdrv_install_key()` now returns a key the chip refused as an error, where it took it as installed or asserted on the index the reply never carried; a MESH-interface build counts an accepted key at another hardware index instead of asserting. The start's `RESULT:` line (`main/mesh.c`, `warthog_mesh_start_result()` in `main/mesh_diag.c`) says what the chip answered. Shown in `AT+MESHCFG?` (`chip_vif=`, `chip_refused`) and `AT+BCNSTAT?` (`chip_irq`, `host_yield`); host-tested by `test_simnode_meshvif{,_off}`, which link the real `umac_interface.c` (`simnode/interface_seam.c`), the existing simnode suites rebuilt with the flag (`*_meshvif`), and `test_chipvif_glue{,_off}`, which run `driver.c`'s status reads and `MESH_CONFIG` bytes, `beacon.c` and `umac_ps.c`. On air on 2026-09-30 (`-meshvif`, two OpenMANET 1.8.0 Pis at RTS threshold 1000 and a second Warthog): `chip_vif=mesh(5) vif_id=0 fallback=0`; the chip accepted `MESH_CONFIG` and the BSS configuration, where on a STA interface it refuses `MESH_CONFIG` and `BSS_BEACON_CONFIG` with status -17 and the mesh runs regardless; SAE peering with all three, host CCMP, Warthog to Warthog pings both ways; a Pi's 1000-byte frames now get a CTS whichever peer registered last, where on a STA interface only that peer's did (`wiki/OpenMANET-Interop.md`, *Frames over about 1000 bytes from a Linux node*); batman mode; beacons host-sent (`chip_irq` 0). On air on 2026-09-30, `warthog-mesh-sae-meshvif` (chip keys on a MESH interface, before the peer-MGTK change below) peered with two OpenMANET Pis under SAE, `AT+KEYINST?` showed our own MGTK at AID 0 and each peer's MTK at its AID, and Warthog to Warthog unicast passed, but every Pi group frame was undecryptable (`AT+RXCHAN?` `nodec grp`, reason 4), its group PREQs included, so the Pis built no path to it. Not measured on a MESH interface: an open mesh, three or more Warthogs, recovery after a chip restart (a restart under an active mesh asserts, so the board reboots), and a soak longer than the 54-minute one on 2026-09-30 (237/240 1000-byte pings from the Pis, 60/60 Warthog to Warthog, no fallback).
- Peers' MGTKs in the chip on a MESH chip interface (`umac_datapath_mesh.c`, `umac_datapath.c`; `warthog-mesh-sae-meshvif`, the SAE build with AMPE keys in the chip and `WARTHOG_MESH_CHIP_VIF_MESH=1`). As morse_driver does (`mac.c` `morse_mac_ops_set_key`: every key that has a station goes in at that station's AID with its own key index, a group key without one at AID 0), a peer's MGTK goes into the chip at the peer's AID as a group key (`INSTALL_KEY` GTK) once AMPE delivers it, beside our own MGTK at AID 0, at a fresh 2^20 TX PN epoch from the shared allocator (`mesh_next_pn_base_()`), or at TX PN 0 as Linux with `AT+GTKPERSTA=2`. It comes out (`DISABLE_KEY` by the chip's index) where mac80211 frees a station's keys when the peer leaves (after `AUTHORIZED` -> `ASSOCIATED`), and when a new key lands at another index or its install fails; a survivor's goes back with its MTK when another peer leaves, and with `AT+REKEY`. `AT+GTKPERSTA=0|1|2` (`main/at.c`, NVS `mesh_gtk` in `main/cfg.c`, read at mesh start in `main/mesh.c`) switches it at run time: the gate reads the mode at once, and `umac_datapath_mesh_service_peer_gtk()`, run by the mesh service tick (`umac_mesh.c`), takes every peer's MGTK out or puts it back. A group frame the chip opened is taken as its transmitter's only when AMPE keyed that peer, the chip holds the peer's MGTK at its AID under the frame's key id, the frame was read off the chip after the last install of a different key there, and no refused `DISABLE_KEY` left a stale key at that AID (`umac_datapath_mesh_peer_gtk_opened()`). The read order is a counter both chip drivers stamp on each page they read (`mmdrv_rx_metadata.read_seq`, `mm6108/pageset.c`, `mm8108/yaps.c`; storage `g_warthog_rx_read_seq`); a fence retires a minute after its install, before the counter can wrap. A refused `DISABLE_KEY` taints that index (mac80211's `KEY_FLAG_TAINTED`) until a `DISABLE_KEY` there succeeds, retried before each install at that AID, or the chip boots (`umac_datapath_mesh_chip_booted()`, called after `mmdrv_init` in `umac_interface.c` and `umac_mmdrv_shim.c`). Every other one stays refused, as `rxdrop` 95 (data) or `mgmt gp own` (group path selection): on a STA chip interface (where a second group key broke group RX, so the chip's only group key is our own MGTK, which every peer holds), with no peer key in the chip, under another key id, from an unkeyed slot, fenced, tainted, or with `AT+GTKPERSTA=0`. Replay stays the host's, as on Linux (morse_driver sets only `RX_FLAG_DECRYPTED`, so mac80211 checks the PN): against the sender's MGTK in its keychain, per TID for data and on the management counter for group path selection, from the Key RSC its AMPE carried. A fresh frame (`ccmp_is_fresh()` in `supplicant_shim/ccmp.c`, over `umac_keys_rx_replay_fresh()`/`connection_keys_rx_replay_fresh()`, which move no counter) has the MIC octets the chip left checked under the sender's MGTK (`warthog_ccm_mic()` in `umac_mesh_ccm.c`, `umac_mesh_rx_chip_mic_note()` in `umac_mesh_rx_crypto.c`) before the replay counter moves; a replay costs no MIC work and is not counted in `rx_grp`/`mgmt_gp`/`mic_ok`. The check only counts until a `mic_ok` proves the chip keeps those octets for that frame class (data, management); from then on a `mic_bad` is dropped (`micdrop`). Residual, as on Linux: a chip that tried our own MGTK at AID 0 after the key at the sender's AID failed the MIC would let a member forge a peer's group frames and push its replay counter until the check is armed; a frame the chip opened under an old key and handed up after the new key's `INSTALL_KEY` answer passes the fence. Shown in `AT+GTKSTAT?` (`per_sta=`, installs, removals, `tainted`, `rx_grp`, `forged`, `mgmt_gp`, `fence`, `taint`, `mic_ok`/`mic_bad`, `mic_arm`, `micdrop`, each peer's key), `AT+GTKPERSTA?` and `AT+MESHFWDSTAT?` `mgmt gp chip`; host-tested by `test_simnode_peergtk_meshvif` (pinned as before by `test_simnode_peergtk` and `_swccmp_meshvif`) and `test_simnode_mfp_meshvif`, against a fake-chip receive model (`simnode_rx_air()` in `simnode/fake_chip.c`) that opens a frame only under a key the chip holds for its transmitter's station, and optionally falls back to AID 0. Measured on air on 2026-10-01: chip firmware 1.17.6 opens a peer's group frames under the key at the peer's AID on a MESH interface; our own MGTK at AID 0 still seals our group frames; `DISABLE_KEY` takes the key out; the chip does not leave the MIC octets intact, so the MIC check never arms. - Fragment reassembly (`umac_datapath.c`, `datapath_defrag.c`/`.h`, `umac_datapath_data.h`, `umac/keys/` key colour, `supplicant_shim/ccmp.c`). Upstream reassembled after the receive path had already parsed and stripped an 802.11s Mesh Control from every fragment, so every fragmented mesh MSDU was corrupt (measured on air on 2026-10-01: an OpenMANET node's chip fragments 1000-byte frames at MCS0 on its own; the fix passed 8/8 at 1000 and 1400 bytes against a node fragmenting at 512 on both meshvif builds). Reassembly now runs right after the per-MPDU decrypt, replay check and Block Ack update, before Mesh Control, the forwarding engine and leaf learning, and keeps the first fragment's header, as mac80211 (`rx.c` `ieee80211_rx_h_defragment`). With mac80211's FragAttacks checks: next fragment number only, one key id and key colour per chain (`umac_key.gen`, new for every key installed but an identical reinstall), consecutive CCMP PNs, the first fragment's frame type, DS bits, addresses, TID and (mesh only; in a BSS QoS bit 8 is TXOP or queue size) Mesh Control bit, no A-MSDU, 1 s from the first fragment; fragments with a group addr1 and plaintext fragments on a keyed link are dropped first. Chains no longer live in the peer record (`struct datapath_defrag_data` is an anchor): one node-wide table of 4, at most 2 a peer, the oldest evicted to begin another; buffers from the heap, not the chip RX pool (`mmdrv_alloc_mmpkt_for_defrag()` is unused); one core timeout for all of them instead of one each, and every received data frame and the mesh service tick sweep expired chains (`datapath_defrag_expire()`, `umac_datapath_defrag_expire()`). A peer's chains are flushed on removal and when its pairwise key changes (`umac_datapath_stad_flush_defrag()`, from `umac_datapath_mesh_set_peer_key()`). Applies to STA and AP too; AP STA removal (`umac_ap.c`) still frees the record without a flush, which now leaves its chains to expire rather than a timeout pointing into freed memory. Mesh data frames also get mac80211's `ieee80211_rx_mesh_check` shape rule before decryption: a group RA must be From DS only, a unicast RA 4-address (rxdrop 89). Counters: `AT+DEFRAG?`. TX is not fixed: when Warthog's own chip fragments, a Linux node loses the frame (host-CCMP builds: every fragment fails the MIC; chip crypto: only the first fragment is decrypted), measured with `AT+FRAG=512`.

**How it's wired:** `main/idf_component.yml` has:

```yaml
morsemicro/halow:
  version: "2.10.4-esp32-1"
  override_path: "../components/halow"
```

The directory is named `halow` (the dependency short name) so the IDF component graph resolves `main`'s `REQUIRES halow` to this fork rather than to a registry pull.

**Upgrade path:** when Morse Micro tags `2.11.x-esp32-N`, re-vendor the new tarball, strip non-ESP32 BSPs + docs again, replay the mesh additions, and bump the `version:` line. The build script (`pre_build_morselib.py`) patches one CMakeLists line at build time; that patch will need to be re-verified against any morselib reorg upstream.

## `components/firmware/` — thin local IDF component shim (not a fork)

**Why it exists:** `morsemicro/halow`'s shims link against `idf::firmware`, but the registry publishes the binary blobs as `morsemicro/firmware` (note the namespace prefix). IDF's component graph won't resolve `idf::firmware` to a prefixed package automatically, so this 60-line shim component sits in between:

- Pulls the `.mbin` blobs from `managed_components/morsemicro__firmware/` (which the registry populates).
- Exposes them under the bare `firmware` component name so `idf::firmware` resolves.
- Picks the right BCF + firmware file based on `CONFIG_MM_BCF_FILE` / `CONFIG_MM_FW_FILE` / `CONFIG_MMHAL_CHIP_TYPE_*` (Kconfig is a direct copy of upstream's).

**Upstream changes that obsolete this:** if Morse Micro renames the registry package to drop the namespace prefix, or if their shim starts using `idf::morsemicro__firmware` directly, this shim can be deleted.

## `scripts/pre_build_morselib.py` — PlatformIO build hook

**Why it exists:** PlatformIO + ESP-IDF + the `morselib` CMake custom command don't compose cleanly out of the box. Three concrete bugs this hook works around:

1. **PlatformIO's section scanner runs `objdump -h` on every `.a` before CMake's custom commands fire** — so `libmorse.a` doesn't exist yet when scanned, the build aborts. The hook pre-runs `ar -M` + `ranlib` + `librarymangler.py` (the upstream Morse symbol-mangler) so the mangled archive exists before PIO scans.
2. **The `components/firmware/` CMake custom-command for objcopying `.mbin → .o` doesn't fire under PIO**, so the hook does the objcopy itself (same flags, same output object names).
3. **morselib's `IMPORTED` target lacks a dep on the custom command that produces its file** — we patch one line into `components/halow/components/morselib/CMakeLists.txt` (in-tree, with a `# warthog:` marker so it's idempotent) to wrap `libmorse.a` in `-Wl,--whole-archive`. A direct `add_dependencies()` would form a cycle.

The hook is wired in `platformio.ini`:

```ini
extra_scripts = pre:scripts/pre_build_morselib.py
```

**Upstream changes that obsolete this:** if PlatformIO's section scanner learns to run after CMake custom commands, or if Morse Micro restructures their CMake to not need the mangler step, this script can shrink or disappear. The `.mbin → .o` objcopy will likely always be needed under PIO until PIO + IDF custom-command timing is fixed.

## What we don't fork

- `morsemicro/firmware` — pulled from the registry as-is into `managed_components/`. No patches.
- `espressif/esp_tinyusb` — registry, no patches.
- `espressif/tinyusb` — registry, no patches.
- ESP-IDF — pinned via the `pioarduino/platform-espressif32` fork (which itself just upgrades the IDF version from PIO's bundled 5.1.4 to 5.5.4 — no code changes).

## Audit checklist for the next morsemicro/halow upgrade

1. Pull the new tarball into a scratch dir.
2. `diff -r` against `components/halow/` to identify upstream changes vs. our deletions.
3. Re-apply: strip non-ESP32 BSPs, strip docs, re-vendor mesh additions.
4. Verify the morselib `CMakeLists.txt` line that `pre_build_morselib.py` patches still exists at the expected location (search for `set_target_properties(morselib PROPERTIES IMPORTED_LOCATION`).
5. Bump `version:` in `main/idf_component.yml`.
6. Smoke build: `pio run -e warthog-us`.
7. Host suite: `make -C components/halow_mesh_compat/test clean all`, then `make -C components/halow_mesh_compat/test clean all SAN=1` (without `clean` the sanitizer run reuses the plain binaries).
8. Bench test through the full bench-test checklist in the README.
