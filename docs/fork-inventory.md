# Fork Inventory

What's local, what's upstream, and what each piece exists to work around. Everything we ship in-tree — nothing is silently vendored or patched in a way that's hard to audit later.

## `components/halow/` — local fork of `morsemicro/halow` (esp-halow main @4e9ba9b855)

**Source:** [https://github.com/MorseMicro/esp-halow](https://github.com/MorseMicro/esp-halow), main at `4e9ba9b855`: tag `2.11.2-esp32-2` plus 6 commits (mm-iot-sdk moved to its 2.12 tag; the `RESET_N` pin mask shifted as `1ULL`; a P4 config pin fix; no version print before it is read; `CONFIG_MM_RESET_SETTLE_MS` between releasing `RESET_N` and the first SPI clocking; `mmhalow_init()` returning `ESP_FAIL` when the transceiver does not boot). Its submodules at that commit: mm-iot-sdk 2.12.3 (`88606f94a9`) and morse-firmware `ea18605f`. The chip firmware the build links is mm-iot-sdk's `framework/morsefirmware/mm6108.mbin`, `rel_1_17_9_2026_Apr_20` (sha256 `aff63921…`).

**Why forked:** the registry version doesn't expose the chip's 802.11s mesh mode — it ships only STA + AP shims. We need umac mesh (`umac_mesh.h`/`umac_mesh.c`-style additions) for the multi-board topologies. See `docs/history/mesh-port-scope.md` for the scope analysis and `docs/history/mesh-port-audit.md` for the umac API audit that informed it.

**Measurements:** every on-air result in this section was taken on the fork's earlier base (`2.10.4-esp32-1`, mm-iot-sdk 2.10.4) with chip firmware `rel_1_17_6_2026_Feb_23`. None has been re-measured on this base or on 1.17.9; the workarounds derived from them (`UMAC_MESH_FRAG_CHIP_MAX` 2, `AT+SEALFIT`, the host-CCMP builds for one pairwise key) stay until they are.

**What's changed relative to upstream:**

- Not vendored: esp-halow's `API.md`, `README.md`, `configs/` and `examples/`; mm-iot-sdk's `framework/doc/`, its prebuilt Arm libraries (`framework/morselib/lib/arm-cortex-*`) and its STM32Cube BSPs (`framework/src/bsps/`). The two submodules (`components/mm-iot-sdk`, `components/firmware/morse-firmware`) are committed as plain files, not gitlinks (morse-firmware's six `bcf_boardtype_*.bin` symlinks as copies of their targets, and without upstream's executable bit on the `.bin` files); `.gitignore` re-includes `components/halow/components/firmware/morse-firmware/**/*.bin`, which its `*.bin` rule would otherwise drop.
- The comment scrub of `83706c6`, which had rewritten "Phase" in 24 vendor files (hostap's EAP peer and server, RADIUS server, `wpa_supplicant/config.h`, `interworking.c`, `eap_example_server.c`; lwIP's `tcp_out.c`), is reverted: those files are byte-identical to upstream's again.
- Mesh additions under `components/halow/components/mm-iot-sdk/framework/morselib/` (`umac/mesh/`, `umac_datapath_mesh.c`, `supplicant_shim/supplicant_core_mesh.c`; `wpa_config_read_mesh()` in `supplicant_shim/config.c`, the mesh hooks in `umac_supp_shim.h`, `umac_supp_shim_data.h` and `umac_supp_shim_private.h`, the Mesh Configuration and Mesh ID element ids in `dot11/dot11.h`); `docs/history/mesh-port-*.md` has the original scope. The mesh lives in upstream's STA interface slot (`umac/interface/umac_interface.c`, `umac_interface.h`, `umac_interface_data.h`): `UMAC_INTERFACE_MESH` is in that slot's type mask, so its chip interface id is the slot's (`umac_interface_get_vif_id(umacd, UMAC_INTERFACE_MESH)`) and mesh RX reaches `main/` as `MMWLAN_VIF_STA`. `umac_mesh_enable_mesh()` calls `umac_interface_add(umacd, UMAC_INTERFACE_MESH, &datapath_ops_mesh, NULL)`, which binds the mesh datapath ops to the slot, replacing a boot scan's; a later scan keeps them, and runs `HW_SCAN` on the mesh's chip interface (not measured on air). The mesh excludes STA and AP: `umac_interface_add()` refuses `MESH` with `MMWLAN_UNAVAILABLE` while the slot holds a STA or a running scan (`UMAC_INTERFACE_SCAN`) or the AP slot is active, and `STA` or `AP` while the mesh is up; a failed `MESH` add puts the slot's previous ops back. `umac_interface_mesh_is_active()` and `umac_datapath_mesh_is_active()` (the slot's ops are `datapath_ops_mesh`, now declared in `umac_datapath.h`) are the only "mesh is up" tests; the datapath looks the ops up per frame, by the RX metadata's VIF, `tx_metadata->vif_id`, or the STA slot then the AP slot on dequeue, as upstream does. While the mesh is up a received frame tagged with no VIF goes to the mesh's (`umac_datapath_rx_frame_preprocess()`, renamed upstream from `_filter`): upstream's VIF table sends a probe request to the AP slot and has no row for a legacy beacon or a broadcast mesh action or data frame. `datapath_ops_mesh` sets upstream's new members: `update_stad_state_rx` (every peer treated as awake, whatever its PM bit), `supp_l2_sock_receive` (a mesh runs no EAPOL: dropped, `g_warthog_mesh_eapol_drop`), `handle_frame_unknown_sta` (data from a node with no slot: counted, `g_warthog_mesh_unknown_ta`), `type` `"MESH"`; both counters print on `AT+RXCHAN?`'s second line (`main/at.c`). A lookup by no address returns a common station record, as the AP's `sta_common`: `umac_datapath_mesh_common_start()` (declared in `umac_mesh.h`, called from the mesh start) allocates it once with the mesh's VIF id, our address as BSSID and SAE or open, PMF off; it is never a peer, never counted, never freed (the mesh has no teardown), and carries frames from unpeered nodes (beacons, SAE, MPM Open) through upstream's per-station checks. `umac_supp_process_mgmt_frame()` (`supplicant_core.c`) hands a frame to the mesh's `wpa_s` whenever one exists, else by VIF to the STA or AP one; the mesh's callers pass `MMWLAN_VIF_STA`.
- Mesh start during a scan (`umac/interface/umac_interface.c` `umac_interface_add()`). A `MESH` add while the STA slot holds `UMAC_INTERFACE_SCAN` is refused with `MMWLAN_UNAVAILABLE` and sends nothing to the chip, as on 2.10.4. Without the check, a `-meshvif` replace removes the VIF a running `HW_SCAN` uses, and on every build the mesh starts under the scan's TX pause (`UMAC_DATAPATH_PAUSE_SOURCE_SCAN`, cleared only when the scan FSM goes inactive; the scan has no timeout): it peers, but no data frame leaves. A completed scan probe (`main/mesh.c`) has left the slot before the mesh start runs. After a probe whose completion never comes, `mmwlan_mesh_enable()` returns `MMWLAN_UNAVAILABLE`, and `umac_mesh_enable_mesh()` logs that another interface is active, not its firmware hint. A scan while the mesh is up is still allowed. Host-tested by `test_simnode_meshvif{,_off}` (19); not measured on air.
- For batman mode (`main/bat_port.c`): `mmwlan_mesh_query_peer_links()` in `include/mmwlan_mesh.h` / `umac/mesh/mmwlan_mesh.c` and `umac_mesh.c` (a peer and rate-control snapshot taken on the umac event loop, via a new `mesh_peer_links` event in `umac/core/umac_core.h`; it returns a status, so a failed query is not an empty peer table; `mmwlan_mesh_get_peer_links()` is the count-only form), `umac_datapath_mesh_peer_links()` in `umac_datapath_mesh.c`, `umac_rc_get_expected_tput_kbps()` in `umac/rc/umac_rc.c` (theoretical throughput of rate control's best rate), and the `g_warthog_mesh_batman` gate in `umac_datapath.c`: with `AT+MESHGRP=0` (default) group frames take the Address Extension mode 2 replica shape, with `1` they stay standard group frames, and leaf proxy learning is off. In the same file a unicast whose RA names a peer AMPE has not keyed yet returns `MMWLAN_NOT_FOUND` instead of being queued and dropped.
- Mesh peer records across tasks (`umac_datapath_mesh.c`, `umac_datapath.c`). Peers are added and deleted on the umac event loop, but `umac_datapath_tx_frame()` (lwIP's tcpip thread, the batman engine task) and the receive filter in `umac_datapath_rx_frame()` (the chip driver task) look them up on their own tasks; in mesh mode both run between `umac_datapath_mesh_read_begin()` and `umac_datapath_mesh_read_end()`. `umac_datapath_mesh_del_peer()` unlinks a peer and takes its queue in one critical section, releases the frames after it, and frees the record only once every reader inside at that moment has left; until then its slot is not reused. Readers alternate between two counts, so later readers cannot hold a record back, and neither side ever waits for the other. `mesh_queue_one_()` queues only to a peer still in the table.
- Receive replay counters per TID for QoS data (`umac/keys/umac_keys.h`, `umac_datapath.c`; the key RSC seeds every TID's counter in `supplicant_shim/driver.c` and `driver_ap.c`), as 802.11 requires and mac80211 does: a peer's frames on two access categories can arrive with their PNs interleaved.
- Receive filter, unicast data not addressed to us (`umac_datapath_rx_frame_preprocess()` in `umac_datapath.c`). In mesh mode the MM6108 hands up unicast data frames addressed to other stations (measured on air on 2026-09-30: another Warthog's frames to an OpenMANET node, which host CCMP then tried under the sender's pairwise key and counted as `micfail`). A mesh data frame whose receiver address (addr1) is unicast and not ours is now dropped after the unknown-sender and own-source checks and before the duplicate check, so it reaches neither the sender's duplicate state, its Block Ack reorder window, host CCMP nor the chip-decrypted path; counted as filter reason 9 (`g_warthog_filt_hist[9]`, now ten entries, in `main/at.c`; `not_ours` in `AT+FILTSTAT?`). An 802.11s unicast relayed through us carries our address in addr1, so relaying is unchanged; group-addressed frames and management frames are not judged. Ahead of the pre-association gate, a mesh unicast management frame other than a beacon whose addr1 is not our mesh address (`umac_mesh_own_addr()`, now declared in `umac/mesh/umac_mesh.h`) is counted and its first 16 octets kept, not dropped (`g_warthog_filt_mgmt_nours` and `g_warthog_filt_mgmt_nours_hdr` in `main/at.c`; `mgmt_nours` on the second line of `AT+FILTSTAT?`): whether the chip hands those up is not measured, and until it is they still reach host CCMP, Block Ack and path selection. STA and AP modes are unchanged: there upstream relies on the chip's own receiver-address filter, which is not measured in those modes. `main/` never enables AP, but enables STA (`main/halow.c` `mmhalow_connect()`, which calls `mmwlan_sta_enable()`) whenever mesh is off and a HaLow SSID is stored: the default on `warthog-station` and `warthog-station-ecm`, where `AT+MESHEN` defaults to 0.
- Block Ack and peer teardown (`umac/ba/umac_ba.c`, `umac_datapath.c`). `umac_ba_deinit()` cancels each TID's pending ADDBA request retry before it clears the sessions; mesh `del_peer` needs this, since the retry otherwise fires on a freed peer record. It also runs on STA disconnect (`umac/connection/umac_connection.c`), so client mode now cancels its retries there too; that path is not host-tested. `umac_datapath_stad_teardown()` (new in `umac_datapath.c`, called with `umac_ba_deinit()` from `umac_datapath_mesh_del_peer()`) cancels the RX reorder timeout and releases the reorder list and defrag state. `umac_datapath_tx_mgmt_frame()` has a mesh branch in place of the STA PMF logic: a robust unicast management frame (Block Ack) to a peer that runs MFP is protected as its path selection is, by `umac_datapath_mesh_protect_mgmt()` in `umac_datapath_mesh.c` — marked for the chip's CCMP, or sealed with host CCMP while it is on (`-swccmp` builds); a frame that cannot be sealed is dropped and counted (`tx_fail` in `AT+SWCCMP?`), never sent in the clear. Each one is also counted in `AT+MESHFWDSTAT?` (`mgmt tx chip`/`host`/`drop`, `g_warthog_mgmt_tx_*` defined in `main/at.c`).
- Group path selection under SAE is group-addressed privacy, as mac80211 does it (`net/mac80211/rx.c` `ieee80211_rx_h_decrypt`, `tx.c` `ieee80211_select_link_key`; 802.11 Table 9-47). In `umac/mesh/umac_mesh.c` our own group PREQs and PERRs go out Protected under our own MGTK, sealed by the chip (`HW_ENC` under its key id, no MMIE; `UMAC_MESH_HWMP_PROT_GROUP` from `umac_datapath_mesh_hwmp_tx_key()`) and counted in flight under that MGTK until their TX status, as our group data is (`mesh.own_group`); before hostap delivers our MGTK, or while its chip install has failed, they go in the clear. Only host CCMP (`-swccmp` builds), or on `warthog-mesh-sae-meshvif` the chip holding the peer's MGTK at its AID (below), can open a peer's, so on the other chip-crypto images Warthogs no longer take each other's. Counted in `AT+MESHFWDSTAT?` (`hwmp gp`, `hwmp tx gp`/`plain`, `mgmt gp nodec`/`own`/`key`/`replay`). Written from mac80211's source and host-tested after an on-air failure against OpenMANET 1.8.0 on 2026-09-29, where every group PREQ was refused; on air on 2026-09-30 the nodes' group PREQs were taken and they held an `ACTIVE` path to the Warthog. Not measured: whether the chip seals our group path selection and, on the swccmp builds (`WARTHOG_MESH_MGTK_PN_BASE`), starts our MGTK at the TX PN `INSTALL_KEY` gives it, which the Key RSC AMPE advertises assumes.
- Mesh chip interface type (`umac/interface/umac_interface.c`, `umac_mesh.c`, `umac_datapath_mesh.c`, `umac/ps/umac_ps.c`, `driver/driver.c`, `driver/beacon/beacon.c` and the host beacon timer fields in `driver/morse_driver/morse.h`). The board boots the chip with a STA-type interface and, by default, the mesh runs on it; with `WARTHOG_MESH_CHIP_VIF_MESH=1` (`warthog-mesh-sae-swccmp-meshvif`, and `warthog-mesh-sae-meshvif` with AMPE keys in the chip) `umac_interface_add(MESH)` replaces it with `ADD_INTERFACE` type 5 and that interface's `GET_CAPABILITIES`, as Linux adds a mesh point, and falls back to a STA interface when the chip refuses it, gives it an id other than 0 (beacons and data are tagged VIF 0), or `REMOVE_INTERFACE` fails. The start's `RESULT:` line (`main/mesh.c`, `warthog_mesh_start_result()` in `main/mesh_diag.c`) says what the chip answered. - Peers' MGTKs in the chip on a MESH chip interface (`umac_datapath_mesh.c`, `umac_datapath.c`; `warthog-mesh-sae-meshvif`, the SAE build with AMPE keys in the chip and `WARTHOG_MESH_CHIP_VIF_MESH=1`). As morse_driver does (`mac.c` `morse_mac_ops_set_key`: every key that has a station goes in at that station's AID with its own key index, a group key without one at AID 0), a peer's MGTK goes into the chip at the peer's AID as a group key (`INSTALL_KEY` GTK) once AMPE delivers it, beside our own MGTK at AID 0, at a fresh 2^20 TX PN epoch from the shared allocator (`mesh_next_pn_base_()`), or at TX PN 0 as Linux with `AT+GTKPERSTA=2`. It comes out (`DISABLE_KEY` by the chip's index) where mac80211 frees a station's keys when the peer leaves (after `AUTHORIZED` -> `ASSOCIATED`), and when a new key lands at another index or its install fails; a survivor's goes back with its MTK when another peer leaves, and with `AT+REKEY`. `AT+GTKPERSTA=0|1|2` (`main/at.c`, NVS `mesh_gtk` in `main/cfg.c`, read at mesh start in `main/mesh.c`) switches it at run time: the gate reads the mode at once, and `umac_datapath_mesh_service_peer_gtk()`, run by the mesh service tick (`umac_mesh.c`), takes every peer's MGTK out or puts it back. A group frame the chip opened is taken as its transmitter's only when AMPE keyed that peer, the chip holds the peer's MGTK at its AID under the frame's key id, the frame was read off the chip after the last install of a different key there, and no refused `DISABLE_KEY` left a stale key at that AID (`umac_datapath_mesh_peer_gtk_opened()`). The read order is a counter both chip drivers stamp on each page they read (`mmdrv_rx_metadata.read_seq`, `mm6108/pageset.c`, `mm8108/yaps.c`; storage `g_warthog_rx_read_seq`); a fence retires a minute after its install, before the counter can wrap. A refused `DISABLE_KEY` taints that index (mac80211's `KEY_FLAG_TAINTED`) until a `DISABLE_KEY` there succeeds, retried before each install at that AID, or the chip boots (`umac_datapath_mesh_chip_booted()`, called after `mmdrv_init` in `umac_interface.c` and `umac_mmdrv_shim.c`). Every other one stays refused, as `rxdrop` 95 (data) or `mgmt gp own` (group path selection): on a STA chip interface (where a second group key broke group RX, so the chip's only group key is our own MGTK, which every peer holds), with no peer key in the chip, under another key id, from an unkeyed slot, fenced, tainted, or with `AT+GTKPERSTA=0`. Replay stays the host's, as on Linux (morse_driver sets only `RX_FLAG_DECRYPTED`, so mac80211 checks the PN): against the sender's MGTK in its keychain, per TID for data and on the management counter for group path selection, from the Key RSC its AMPE carried. A fresh frame (`ccmp_is_fresh()` in `supplicant_shim/ccmp.c`, over `umac_keys_rx_replay_fresh()`/`connection_keys_rx_replay_fresh()`, which move no counter) has the MIC octets the chip left checked under the sender's MGTK (`warthog_ccm_mic()` in `umac_mesh_ccm.c`, `umac_mesh_rx_chip_mic_note()` in `umac_mesh_rx_crypto.c`) before the replay counter moves; a replay costs no MIC work and is not counted in `rx_grp`/`mgmt_gp`/`mic_ok`. The check only counts until a `mic_ok` proves the chip keeps those octets for that frame class (data, management); from then on a `mic_bad` is dropped (`micdrop`). Residual, as on Linux: a chip that tried our own MGTK at AID 0 after the key at the sender's AID failed the MIC would let a member forge a peer's group frames and push its replay counter until the check is armed; a frame the chip opened under an old key and handed up after the new key's `INSTALL_KEY` answer passes the fence. Measured on air on 2026-10-01: chip firmware 1.17.6 opens a peer's group frames under the key at the peer's AID on a MESH interface; our own MGTK at AID 0 still seals our group frames; `DISABLE_KEY` takes the key out; the chip does not leave the MIC octets intact, so the MIC check never arms. - Fragment reassembly (`umac_datapath.c`, `datapath_defrag.c`/`.h`, `umac_datapath_data.h`, `umac/keys/` key colour, `supplicant_shim/ccmp.c`). Upstream reassembled after the receive path had already parsed and stripped an 802.11s Mesh Control from every fragment, so every fragmented mesh MSDU was corrupt (measured on air on 2026-10-01: an OpenMANET node's chip fragments 1000-byte frames at MCS0 on its own; the fix passed 8/8 at 1000 and 1400 bytes against a node fragmenting at 512 on both meshvif builds). Reassembly now runs right after the per-MPDU decrypt, replay check and Block Ack update, before Mesh Control, the forwarding engine and leaf learning, and keeps the first fragment's header, as mac80211 (`rx.c` `ieee80211_rx_h_defragment`). With mac80211's FragAttacks checks: next fragment number only, one key id and key colour per chain (`umac_key.gen`, new for every key installed but an identical reinstall), consecutive CCMP PNs, the first fragment's frame type, DS bits, addresses, TID and (mesh only; in a BSS QoS bit 8 is TXOP or queue size) Mesh Control bit, no A-MSDU, 1 s from the first fragment; fragments with a group addr1 and plaintext fragments on a keyed link are dropped first. Chains no longer live in the peer record (`struct datapath_defrag_data` is an anchor): one node-wide table of 4, at most 2 a peer, the oldest evicted to begin another; buffers from the heap, not the chip RX pool (`mmdrv_alloc_mmpkt_for_defrag()` is unused); one core timeout for all of them instead of one each, and every received data frame and the mesh service tick sweep expired chains (`datapath_defrag_expire()`, `umac_datapath_defrag_expire()`). A peer's chains are flushed on removal and when its pairwise key changes (`umac_datapath_stad_flush_defrag()`, from `umac_datapath_mesh_set_peer_key()`). A chain's buffer carries room for RX metadata (`FRAG_CHAIN_MD_SPACE`) and `datapath_defrag_begin()` copies the first fragment's whole, so a reassembled MSDU's `mmdrv_get_rx_metadata()` is valid where upstream's Block Ack reorder path reads it. Upstream's new management-frame reassembly (`process_rx_other_frame()`) runs through the same `datapath_defrag()` and its checks: a group-addressed management fragment is dropped (rxdrop 7, `mcast`), a protected one is opened and its 8-octet MIC stripped on its own (`umac_datapath_process_mgmt_frame_ccmp_header()`), its key id, colour and PN going to the chain, and the reassembled frame is not opened again; plaintext management fragments are reassembled as plaintext and judged whole by the management path's MFP rules. - Driver command status (`internal/mmdrv.h`, `driver/driver.c`, `driver/morse_driver/command.c`, `common/morse_commands.h`). Upstream's `mmdrv_*` return `enum mmwlan_status`, and its `morse_cmd_tx()` returns `MMWLAN_COMMAND_ERROR` when the chip's reply carries a non-zero status, still copying the reply. The fork's helpers keep the chip's verdict apart from the transport's: `mmdrv_add_if_status()`, `mmdrv_get_capabilities_status()`, `mmdrv_update_sta_state_status()`, `mmdrv_install_key_status()`, `mmdrv_set_bssid()`, `mmdrv_cfg_bss_beacon()` and `mmdrv_mesh_config()` return `MMWLAN_SUCCESS` whenever the chip answered and write its status to `*chip_status` (non-zero: refused), and return any other status (`MMWLAN_TIMED_OUT`, `MMWLAN_NOT_RUNNING`, `MMWLAN_NO_MEM`, ...) with `*chip_status` unwritten, so callers initialise it. They pass `skip_errlog`, which drops `morse_cmd_tx()`'s closing `ERR` line on a transport failure (`timed out`, `failed with rc`), so `morse_cmd_tx()` logs a timeout only with its per-try `INF` line; `morse_cmd_tx()` never logs a chip refusal at `ERR`, whatever `skip_errlog` says. A VIF id and capabilities are written only when the chip accepted, and a refused key leaves `key_conf` as it was. The plain `mmdrv_add_if()`, `mmdrv_update_sta_state()`, `mmdrv_install_key()` and `mmdrv_get_capabilities()` run through them and return `MMWLAN_COMMAND_ERROR` on a refusal, as upstream's do; upstream's passed `skip_errlog` false, so on the STA, AP and boot paths a timeout of these four no longer logs `morse_cmd_tx()`'s `ERR` line (its per-try `INF` line and the caller's own `WRN`, where it has one, remain). Fork code takes any driver result but `MMWLAN_SUCCESS` as a failure (`hw_scan.c` tests `!= 0`, the same value), and `MMDRV_VIF_ID_INVALID` (0xffff) is the only invalid VIF id. `AT+MESHCFG?` `add_st=` holds the chip's status for a refused MESH interface, 14 (`MMWLAN_COMMAND_ERROR`) when the chip refused to remove the boot interface (`mmdrv_rm_if()` keeps no chip status), any other positive `mmwlan_status` for a failed `ADD_INTERFACE` or `REMOVE_INTERFACE` transport, and `-1000-<id>` for a MESH interface given an id other than 0; `AT+DATASTAT?` `last_err=` is the `mmwlan_status` of the last whole data frame `mmdrv_tx_frame()` failed (`umac_datapath_process_tx_frame()`); a failed host fragment counts in `drv_err` and `AT+HOSTFRAG?` `drv` but leaves it, and a failed management frame or QoS Null counts in neither. `AT+CRYPTOHOST?` `rc=` is the last request's `mmwlan_status` (0 taken, 14 refused by the chip, 6 timed out, 10 driver not running, 5 out of memory; on 2.10.4 it was 0 for any chip answer); after a failed request `value=` is 0xffffffff, not a read-back, and a refused setting is not restored after a chip restart. `mmdrv_set_crypto_in_host()` and `mmdrv_get_crypto_in_host()` zero their response, so a reply short of its value reads 0, not stack. The fork's own commands (`MESH_CONFIG` 0x0039, `MCAST_FILTER` 0x003C, `BSS_BEACON_CONFIG` 0x003D, `BSSID_SET` 0x0052) keep their layouts under upstream's command semver 57 (was 56; the 12-octet header is unchanged); whether chip firmware 1.17.9 takes them is not measured.
- Reply status (`driver/morse_driver/command.c`, `morse_cmd_tx()`). ## `scripts/pre_build_morselib.py` — PlatformIO build hook

**Why it exists:** PlatformIO + ESP-IDF + the `morselib` CMake custom command don't compose cleanly out of the box. Two concrete bugs this hook works around (a third is obsolete):

1. **PlatformIO's section scanner runs `objdump -h` on every `.a` before CMake's custom commands fire** — so `libmorse.a` doesn't exist yet when scanned, the build aborts. The hook pre-runs `ar -M` + `ranlib` + `librarymangler.py` (the upstream Morse symbol-mangler) so the mangled archive exists before PIO scans.
2. *(Obsolete.)* The hook objcopied the registry's `.mbin` blobs into objects, because the old `components/firmware/` custom command did not fire under PIO. The bundled `morsefirmware` library embeds them now, so that half of the script is removed and `append_firmware_link_flags()` appends only the whole-archive `libmorse.a`. If `nm firmware.elf` lacks the four blob symbols, objcopy the two files here again under those names.
3. **morselib's `IMPORTED` target lacks a dep on the custom command that produces its file** — we patch one line into `components/halow/components/morselib/CMakeLists.txt` (in-tree, with a `# warthog:` marker so it's idempotent) to wrap `libmorse.a` in `-Wl,--whole-archive`. The marker is committed, so on this tree the hook finds it and changes nothing. A direct `add_dependencies()` would form a cycle.

The hook is wired in `platformio.ini`:

```ini
extra_scripts = pre:scripts/pre_build_morselib.py
```

**Upstream changes that obsolete this:** if PlatformIO's section scanner learns to run after CMake custom commands, or if Morse Micro restructures their CMake to not need the mangler step, this script can shrink or disappear.

## Audit checklist for the next morsemicro/halow upgrade

1. Pull the new esp-halow and both submodules (mm-iot-sdk, morse-firmware) into a scratch dir.
2. Strip it as in the first entry above, the previous upstream the same way, and diff the two to see upstream's changes.
3. Three-way merge (base: the previous upstream, stripped; ours: `components/halow/`; theirs: the new one, stripped) and replay the entries above. Check every fork call against changed upstream signatures and return types, and every helper the fork removed or renamed.
4. Verify the morselib `CMakeLists.txt` line that `pre_build_morselib.py` patches still exists at the expected location (search for `set_target_properties(morselib PROPERTIES IMPORTED_LOCATION`).
5. Check the build configuration against the new Kconfig: every `sdkconfig.defaults` symbol still exists (`scripts/ci/check-sdkconfig-landing.sh`), and new defaults (`MM_CHIP`, `HALOW_AP_MODE`, `HALOW_PS_MODE`, `MM_RESET_SETTLE_MS`) are set on purpose. Check the firmware the bundled CMake links (`strings mm6108.mbin | grep rel_`) and that the BCF is still the committed 540 bytes (sha256 `9553cadb…f54f765`).
6. Bump `version:` in `main/idf_component.yml`.
7. Before the first build on the new tree, clear what PlatformIO and the component manager keep: `rm -f sdkconfig.warthog-*`, `rm -rf .pio/build dependencies.lock`, and every `managed_components/` entry the manifest no longer names (this rebase: `managed_components/morsemicro__firmware`). Configure loads `sdkconfig.defaults` first and an existing sdkconfig over it, so the old file keeps every value it sets itself (a line with no `# default:` above it, every value it took from `sdkconfig.defaults` among them) and a value `sdkconfig.defaults` changes for one of those never reaches it (`scripts/ci/check-sdkconfig-landing.sh` reports it); a symbol it does not name, or names only as a Kconfig default (`# default:`), such as this rebase's `CONFIG_MM_CHIP_MM6108` and `CONFIG_HALOW_AP_MODE`, takes `sdkconfig.defaults`.
8. Smoke build: `pio run -e warthog-station`; `nm` the ELF for the four blob symbols.
9. Host suite: `make -C components/halow_mesh_compat/test clean all`, then `make -C components/halow_mesh_compat/test clean all SAN=1` (without `clean` the sanitizer run reuses the plain binaries). Inputs that follow upstream: the shims include directory the simnode uses (`components/shims/include/<arch>`), the real sources it links (`SIMNODE_REAL`, `HWSCAN_SRCS`, `CHIPVIF_DEPS`, `ELOOP_SRCS` in the `Makefile`) and the functions it extracts by name (`CHIPVIF_FNS`, `CMDSTATUS_FNS` with `ps.c`'s setter, `SDIO_FNS` with `sdio.c`'s `spi_irq` globals), the generated fake radio stack (`simnode/regen_stubs.sh`), the fake chip's driver signatures (`simnode/fake_chip.c`), `make region-bcf`, and the glue guards that pin vendor text (`test_glue_guard.sh`; each names the text it pins).
10. Bench test through the full bench-test checklist in the README, and re-measure the chip workarounds (fragment cap, `AT+SEALFIT`, per-AID keys, MIC octets) on the new chip firmware before removing any.
