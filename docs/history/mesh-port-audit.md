# Audit Findings — Internal API Visibility & Mangler

**Task:** #2 (audit chip command paths used by AP code in morselib source)
**Date:** 2026-05-16
**Outcome:** Original "sibling component" plan from `mesh-port-scope.md` is blocked. Three viable paths remain; recommendation below.

## What the audit found

### 1. Internal umac API exists and is well-structured for adding new modes

`components/morselib/CMakeLists.txt` line 6–12:

```cmake
set(INC
    ${ROOT_DIR}/include
    ${ROOT_DIR}/src
    ${ROOT_DIR}/src/internal       # ← internal headers ARE exposed
    ${ROOT_DIR}/src/umac/rc/mmrc_osal
    ${ROOT_DIR}/mmrc/src/core
)
```

`umac_ap.h` (in the internal tree) declares:
- `umac_ap_enable_ap(struct umac_data *, const struct mmwlan_ap_args *)` — entry point from public `mmwlan_ap_enable()`
- `umac_ap_start(struct umac_data *, const struct umac_ap_config *)` — beacon-up
- `umac_ap_get_beacon(struct umac_data *)` — beacon template
- `umac_ap_handle_probe_req(...)`, `umac_ap_add_sta(...)`, etc.

So a `umac_mesh.h/c` mirroring this structure is a sensible shape. Header surface is clean.

### 2. The mangler renames every non-public symbol

`components/morselib/CMakeLists.txt` line 105–142 runs `librarymangler.py` on the linked `libmorse.a + libhostap` archive. From `librarymangler.py`:

```python
def _hash_symbol_name(symbol_name):
    return f'mmint_{hashlib.sha256(symbol_name.encode("utf-8")).hexdigest()[0:8]}'
```

Protected (i.e. NOT mangled) symbol patterns in `tools/metadata/protected_syms.txt`:

```
mbedtls_*
mmosal*
mmhal*
mmiperf*
mmping*
mmport*
mmwlan*
mmconfig*
mmpkt*
mmint*
emmet_init
emmet_set_reg_db
emmet_start
printf
vprintf
putchar
puts
setvbuf
mm_hexdump
morse_xtal_init_delay
```

Anything else — `umac_ap_*`, `umac_data` accessors, `morse_cmd_*` dispatch, all internal umac primitives — gets renamed to `mmint_<8-hex-chars>` in the final archive. This matches the `mmint_6607872b` / `mmint_700c7a34` / `mmint_82209b11` / `mmint_f60fd2ae` undefined-references we saw during the earlier Meshtastic-variant linking experiment.

**Consequence:** A sibling `warthog_mesh` component cannot call `umac_*` functions by name. Header declarations exist, but the symbols don't exist under those names in the linked library.

### 3. License of morselib source

`SPDX-License-Identifier: GPL-3.0-or-later OR LicenseRef-MorseMicroCommercial`

This applies to the umac sources we'd want to extend. The Apache-2.0 on the registry component metadata is for the wrapper/CMake glue only. Implication: any derivative of morselib (including a fork that adds files) is GPL-3.0.

### 4. Chip-side mesh ABI confirmed open

`morse_commands.h` from the GPL Linux driver (`MorseMicro/morse_driver`, semver 56.17.0, autogenerated) defines:

- `MORSE_CMD_INTERFACE_TYPE_MESH = 5` in `enum morse_cmd_interface_type`
- `MORSE_CMD_ID_MESH_CONFIG = 0x0039` with `struct morse_cmd_req_mesh_config { opcode, enable_beaconing, mbca_config, min_beacon_gap_ms, mbss_start_scan_duration_ms, tbtt_adj_timer_interval_ms }`
- `MORSE_CMD_ID_IBSS_CONFIG = 0x0035`
- `MORSE_CMD_ID_BSS_BEACON_CONFIG = 0x003D`
- `MORSE_CMD_ID_SET_OFFSET_TSF = 0x003A`

The chip firmware blob shipping in the registry component accepts these commands — that's a property of the firmware, not the host driver. Same `mm6108.mbin` is used by the Linux driver in mesh mode and by morselib in STA/AP mode.

## What still works from the original scope

- `mmwlan_mesh.h` public API design — unchanged.
- `mmwlan_mesh.c` skeleton at the public-API layer — unchanged.
- Vendored hostap `mesh.c` / `mesh_mpm.c` / `mesh_rsn.c` — we can still glue these in.
- Effort sequencing (~10 weeks) — modulo a small bump for one of the path options below.

## Three viable paths forward

### Path A — Local fork of `morsemicro__halow`

- Copy `managed_components/morsemicro__halow/` into `components/morsemicro_halow_local/` (or similar).
- Add `idf_component.yml` override so the local copy supersedes the registry one.
- Add our `umac/mesh/` source files to `morselib/CMakeLists.txt`'s SRCS list.
- Add `umac_mesh*` to `protected_syms.txt` (so our entry points aren't mangled into oblivion).
- Build umac/mesh against morselib's internal headers directly.

**Pros:** mesh code lives inside the same compilation unit as umac/ap, so all internal symbols are reachable; no mangler issues.

**Cons:** Component updates from Morse have to be manually merged into our fork. Total tree size grows by ~30 MB (the entire vendored component). The whole Warthog firmware becomes GPL-3.0 (or requires a commercial license from Morse) once we link against modified morselib source.

**Effort delta vs original 10-week estimate:** +0–1 week for fork setup + tracking.

### Path B — Add `umac_mesh*` to the registry component's protected list, otherwise treat as sibling

A narrower fork: only modify `protected_syms.txt` (to whitelist `umac_mesh*`, `umac_data*`, etc. as needed) and the morselib CMakeLists' SRCS to include our `umac/mesh/` files. Keep everything else from the registry.

**Pros:** smaller diff than full fork; easier to rebase.

**Cons:** Still a fork in practice (CI overlay or pre-build hook to apply the diff). Same GPL implications. We'd need every symbol our umac/mesh files reach into to be whitelisted, which expands the protected list considerably (umac_data accessors, command dispatch, event loop, datapath hooks).

**Effort delta:** +0.5 week for the overlay tooling, but ~1 week of mapping out which internal symbols we need to whitelist.

### Path C — Reimplement the host driver layer from scratch on the open shim

Bypass morselib entirely for mesh. Talk to the chip via the open-source `shims/mmhal_*` SPI layer, sending `MORSE_CMD_ID_MESH_CONFIG` and friends framed per the open `morse_commands.h`. Implement our own page-ring TX/RX, command dispatch, event handling, and umac state machine — all from scratch.

**Pros:** No fork, no GPL contamination (we'd use the Apache-2.0 shims + our own Apache-2.0 code). Clean license story for Warthog as a whole.

**Cons:** Largest engineering scope. We'd be reimplementing what morselib already does — the page-ring protocol, command framing/sequencing, event loop, datapath. This is essentially the original "port morse_driver" estimate. **~13–16 weeks**, not 10.

**Effort delta:** +4–6 weeks vs Path A.

## Recommendation

**Path A** (local fork) if the goal is to ship mesh on Warthog quickly and we accept GPL-3.0 for the firmware.

**Path C** (clean-room reimplementation) if Warthog must stay permissively-licensed.

**Path B** is a worst-of-both — the fork tax without the convenience of just having the whole tree at hand. Don't recommend.
